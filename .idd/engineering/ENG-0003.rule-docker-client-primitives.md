# ENG-0003.rule-docker-client-primitives

## Rule

Use a thin custom Docker Engine API client as the primary production integration. Use System.Text.Json for Docker JSON, HttpClient with SocketsHttpHandler for ordinary Engine HTTP requests/response streams, and NamedPipeClientStream for Windows named-pipe transport. Use Task-based asynchronous operations, CancellationToken for cancellation, and bounded `Channel<T>` for buffered asynchronous stream delivery.

Docker.DotNet is not the primary production client, and docker CLI output is not the regular resource/logs/stats transport.

## Applicability

Conditional

## Applies when

- Implementing or changing Docker API integration, serialization, connection transport, asynchronous Engine operations, or buffered stream/session delivery.

## Rationale

The MVP technology decision table explicitly selects these client and .NET primitives. The project needs direct control over negotiated schemas, streaming output, and duplex exec. IDD-0012 records the integration rationale; product contracts remain in the relevant Intent specs.

## Guidance

Keep the protocol implementation behind the application boundary from ENG-0002. Ordinary requests can use a supplied pipe stream with SocketsHttpHandler. Manage duplex exec attachment separately when ordinary HTTP response handling does not provide the required bidirectional stream.

Do not let ordinary short-request timeouts terminate long-running events, logs, stats, or exec sessions. Use explicit per-operation cancellation and suitable short-request lifetimes. The source's numerical timeout and connection-limit examples are not fixed policy.

Docker CLI context discovery and Docker.DotNet prototype/reference use are compatible with this rule; neither replaces the selected production integration. Do not copy illustrative method signatures, frame-size constants, or directory layouts as additional constraints.

## Verification

Integration evidence demonstrates the selected primary client, JSON/HTTP/pipe primitives, explicit cancellation, bounded channel delivery, and a functioning attached exec path. Ordinary resource/logs/stats operations do not depend on parsing CLI output or using Docker.DotNet as their primary client.
