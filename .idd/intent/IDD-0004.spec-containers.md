# IDD-0004.spec-containers

## Intent

Find and diagnose all containers on the selected Engine and perform safe, state-aware lifecycle actions.

## Related Specifications

IDD-0003, IDD-0005, IDD-0006, IDD-0007, IDD-0008, IDD-0009, IDD-0010.

## Behavior

- List both running and stopped containers, with identity, name, image, state/status, health when available, ports, and creation/start information.
- Search by name, short/full ID, image, and status without blocking the interface.
- Show actual container details, mounts, network relationships, raw Inspect, and the diagnostics owned by IDD-0009.
- Provide Start, Stop, Restart, and Delete according to current state. Created/exited containers can be started; running containers expose stop/restart and their live tools.
- Paused, restarting, and dead states are represented accurately. Showing a paused state does not require Pause/Unpause commands.
- Mark lifecycle operations pending and establish the result from current Engine state, including concurrent external actions and a lost response.
- Default container deletion uses force=false and v=false. It must not implicitly delete associated volumes.
- A running container requires stopping first or an explicitly dangerous Force Delete choice. Confirmation makes the chosen operation clear.
- If the container disappears externally, remove stale resource state and terminate its views or sessions gracefully.

## Product-Significant Architecture And Constraints

The list contract includes all container states. The Engine decides whether an operation is permitted; local state-based affordances cannot eliminate races. IDD-0006 owns reconciliation after commands, and IDD-0002 owns daemon error semantics.

### Optional bulk scope

Multi-select lifecycle operations are optional in the source and are not mandatory initial scope. If offered, concurrency is bounded and outcomes are reported per item; partial failure must never be hidden. The numerical concurrency recommendation is not an imported requirement.

## Non-goals

- Creating containers or implementing Compose orchestration.
- Requiring Pause/Unpause in the MVP.
- Automatically selecting force deletion or deleting volumes with a container.

## Acceptance Criteria

- Running, stopped, and transitional container states are visible and searchable.
- Start/Stop/Restart converge on the same actual state visible to an external Docker client.
- Canceling deletion sends no delete request.
- Default deletion leaves volumes intact, and deleting a running container never silently escalates to force.
- A lost response or external state race resolves through inspection/reconciliation rather than a repeated blind mutation.

## Verification

Evidence includes lifecycle transitions, running-container deletion, preserved volumes, concurrent CLI actions, conflict/not-found responses, lost mutation responses, and external deletion while a detail or log view is active.
