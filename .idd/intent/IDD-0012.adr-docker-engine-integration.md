# IDD-0012.adr-docker-engine-integration

## Status

Accepted

## Context

The MVP requires resource APIs, negotiated compatibility, logs/events/stats streams, and a duplex exec session over local Windows transport. The source's MVP technology decision table selects a thin custom Engine API client. Its surrounding research explains why conventional REST-only integration or opaque typed-client behavior is insufficient for the full streaming/terminal scope.

## Decision

Integrate directly with Docker Engine HTTP and attached exec contracts through a thin custom client. The current implementation technology and layering constraints are owned by ENG-0002 and ENG-0003; this ADR owns their integration rationale.

Ordinary resource actions and streams use the actual Engine contracts and negotiated API. Docker CLI usage is limited to context discovery rather than serving as the primary resource/logs/stats transport.

## Alternatives Considered

- Docker.DotNet as the sole production client: the source instead chooses explicit control of supported schemas, stream framing, and exec behavior. Use as a research/reference tool does not make it the primary production dependency.
- Parsing regular docker CLI output: does not provide the selected direct Engine protocol boundary.
- A generated REST client alone: does not resolve duplex exec and special stream behavior.
- Unstructured raw HTTP throughout the UI: loses the selected separation between product interactions and Docker integration.

## Consequences

The project owns API negotiation, DTO compatibility, stream decoding, error handling, and the duplex exec integration. Protocol behavior can be verified independently of the UI, and platform transport differences remain isolated.

No current Docker library/daemon version claim from the research is treated as a permanent compatibility promise. Concrete supported schema versions require evidence under IDD-0002.

## Supersedes

None.
