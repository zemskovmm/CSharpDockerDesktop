# IDD-0006.spec-state-reconciliation

## Intent

Keep resource state consistent with the selected Engine despite external operations, missed or duplicate events, reconnects, and uncertain mutation outcomes.

## Related Specifications

IDD-0002, IDD-0004, IDD-0005, IDD-0007, IDD-0008, IDD-0009, IDD-0011.

## Behavior

- Connection and reconnect produce fresh authoritative snapshots of Containers, Images, Volumes, and Networks.
- Events prompt invalidation/selective refresh; they do not become a durable substitute for Engine resource state.
- Events received during initial synchronization are buffered, then replayed/reconciled against the completed snapshot so concurrent changes are not lost.
- Duplicate events and repeated reconciliation do not duplicate resources or produce contradictory state.
- Reconnect resumes event observation with a small overlap where applicable, refreshes the complete snapshot, and reconciles buffered observations.
- External CLI operations update the UI automatically. User-requested full refresh remains available.
- Resource not-found responses remove stale entities and end relevant sessions gracefully.
- Lifecycle commands are pending until their actual outcome is established. Success, conflict, and a lost response all lead to inspection/reconciliation as needed.
- A lost mutation response is an unknown outcome; do not blindly retry a command that may already have succeeded.

## Product-Significant Architecture And Constraints

Events are a synchronization aid, not a durable queue or authoritative property patch log. Resource identity remains scoped to the selected connection. The resource snapshot is in memory; a new application session obtains current Engine state rather than trusting a persisted resource cache.

Cancellation and disconnect must release superseded requests and streams. The source proposes periodic full reconciliation, but the 60–120 second interval is not an imported fixed requirement.

## Non-goals

- Persisting resource snapshots or event history as a competing resource database.
- Promising replay of every historical daemon event.
- Using an uncertain command response as permission for an automatic repeated mutation.

## Acceptance Criteria

- External start/stop/delete actions converge on current GUI state.
- An event arriving before or after a snapshot does not leave a deleted resource present or lose a new resource indefinitely.
- Restarting the daemon restores event observation and fresh resource state without duplicate rows or a GUI restart.
- A mutation applied before the connection drops is recognized through actual state rather than repeated blindly.

## Verification

Evidence covers events on both sides of snapshot completion, duplicate/high-resolution event timestamps, disconnect overlap, full resync, external deletion, command/event races, and lost responses. The resulting visible resources must agree with the Engine's authoritative snapshot.
