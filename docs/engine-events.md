# Negotiated Engine event observations

A successful Engine connection also implements the Application `IEngineEventSource` borrowed capability. `SubscribeEventsAsync` observes containers, images, volumes and networks through the selected API's `/events` endpoint. It does not update resource snapshots, reopen failed streams, deduplicate observations, or schedule reconciliation. Those behaviors belong to Application coordination; authoritative reads remain necessary.

Consumers own `IEngineEventSubscription`, read `Events` until the channel completes, then inspect `Completion` for its classified failure. Completion is a result, not an exception containing daemon data. Explicit token cancellation or disposal completes normally with null. Stream EOF without cancellation reports `UnexpectedEnd`; HTTP, access, malformed/oversized input, opening deadline and transport loss remain distinct. Original bounded daemon error messages remain separate from fixed descriptions. Neither events, actor metadata nor daemon messages are automatically logged.

`EngineEventTimestamp` retains nullable signed 64-bit Unix seconds and nanoseconds independently, without conversion to floating point or DateTime ticks. Missing optional identity/actor attributes/scope/timestamps remain null; an explicitly empty identity or attributes object stays empty. Type and action are required strings. Unknown actions, attribute names and additive JSON fields are accepted. Actor attributes retain their string values and are exposed through a read-only dictionary. Identical timestamps and identical repeated observations are delivered separately.

An optional `EngineEventCursor` encodes nonnegative Unix seconds plus a 0–999,999,999 nanosecond fraction as invariant `seconds.nnnnnnnnn`. The caller chooses an earlier cursor for reconnect overlap. A null cursor omits `since`; no `until` is sent. Type filters and the cursor are URL encoded. Replay is an aid to synchronization and carries no guarantee of complete daemon history.

## Transport ownership and lifetime

Each selected connection owns its ordinary one-connection HTTP/pipe pool. A subscription owns a second independent one-connection pool, negotiated through readiness/version/info before opening events. Its Engine ID (including honest missing values), Engine version, API range/selection and OS type must agree with the selected connection. This bounds a connection to two concurrent pipes and permits liveness, listing and inspection while the event response remains active. Opening the independent pool does not change the ordinary pool's continuity generation.

A pipe replacement *inside either pool* changes that pool's generation and raises continuity invalidation. Ordinary resource operations still reject replaced transports rather than use stale negotiated metadata. The event producer and guarded channel reader reject invalidated observations, cancel blocked delivery/reads, clear pending data on transport loss, and require renewed negotiation. A new concurrent pool negotiates independently; it cannot infer daemon identity from opening a pipe alone. Matching metadata is not proof that a daemon has never restarted: Docker may retain ID/version across restart. Authoritative snapshots and reconnect reconciliation remain required.

One subscription slot includes opening, running, completed and disposal work. A completed or canceled subscription must be disposed before another can open. The owner holds its borrowed subscription, so connection disposal cancels and joins even an in-progress opening. A failed opening cleans up and frees the slot before returning. Subscription disposal cancels blocked reads/channel writes, joins the producer, closes the response and dedicated pool, clears pending delivery and detaches continuity/cancellation registrations. Repeated/concurrent disposal is idempotent; use after connection disposal is rejected. No automatic retry occurs.

The opening deadline covers the independent negotiation, response headers and stream acquisition. The ordinary handshake's per-request deadline also bounds its individual steps. After opening, only explicit cancellation, connection disposal, continuity invalidation or stream failure ends the response; ordinary request timeouts do not govern its duration. `HttpClient.Timeout` is infinite, with explicit per-operation deadlines.

## Buffer budgets

`DockerConnectionOptions` has finite validated defaults: 10-second total opening deadline, 64 KiB per event, and 128 channel entries. These are implementation defaults, not performance promises. Limits are configurable within validated bounds. The newline decoder retains one fixed-size event buffer and a 4 KiB read chunk; delivery retains at most the configured channel capacity plus the producer's one pending observation. `Channel<T>` uses wait/backpressure mode, never drop mode. A slow consumer stops decoding/reading rather than silently losing events. Event size includes bytes before the newline delimiter; a record exactly at the limit is accepted. JSON nesting is also bounded by System.Text.Json's default depth. Error responses retain at most `MaximumResponseBytes`.

## Official schema/history evidence

On 2026-10-14 all 17 official OpenAPI specifications from API 1.40 through 1.56 were downloaded from `https://docs.docker.com/reference/api/engine/version/v1.N.yaml`. Their SHA-256 digests and projected EventMessage/EventActor field types are recorded in `tests/CSharpDockerDesktop.Connection.Tests/Fixtures/Events/schema-evidence.json`. The six core fields are the same throughout: Type, Action, Actor, scope, time and timeNano; Actor defines ID and string-valued Attributes. The timestamps use integer/int64. The per-version JSONL fixtures are clearly synthetic observations derived from those schemas, with four resource types and additive fields; they are not daemon runtime captures.

The [API 1.40 reference](https://docs.docker.com/reference/api/engine/version/v1.40/) and [API 1.56 reference](https://docs.docker.com/reference/api/engine/version/v1.56/) establish the selected fields, resource type filters and `since` query. The [official version history](https://docs.docker.com/reference/api/engine/version-history/) records prune observations with a reclaimed attribute in 1.41, image create observations in 1.46, content negotiation in 1.52, removal of deprecated status/id/from fields in 1.52, and application/jsonl negotiation in 1.53. The decoder uses the modern Actor/Action fields throughout and treats old status/id/from as additive ignored fields; it does not depend on their presence. It preserves arbitrary actions/attributes, including future additions.

The request explicitly sends `Accept: application/json`, retaining Docker's newline-delimited JSON stream across the range. Returned application/json, application/x-ndjson and application/jsonl use the same decoder. RFC7464 JSON sequence framing is not requested; an unexpected incompatible media type is a visible protocol failure. Record boundaries come from the JSON encoder's newline, independent of HTTP chunk boundaries. Moby's [events route implementation](https://github.com/moby/moby/blob/master/daemon/server/router/system/system_routes.go) uses JSON encoding and flushes event delivery.

## Verification and limitations

The independent net10.0 harness passes **54/54 groups on macOS 26.7.1**, with zero build warnings/errors. Its event checks cover all supported schema fixtures; one-byte UTF-8 fragmentation and coalesced reads; precise/duplicate observations; optional fields; encoded overlap cursors; bounded slow-consumer backpressure and single-subscription admission; exact/oversized/truncated/malformed input; preserved HTTP diagnostics and denied access; unexpected EOF and transport loss; opening deadlines; established duration beyond ordinary timeout; cancellation/disposal races, including late opening responses and blocked delivery; independent negotiation and continuity rejection.

The named-pipe fixture uses actual NamedPipeClientStream, SocketsHttpHandler and two concurrent server pipes, with fragmented HTTP chunks carrying duplicated observations while liveness/list/inspect remain successful on the ordinary pipe. Closing the stream releases its pipe without interrupting the ordinary connection. Existing connection/continuity and resource/presentation groups remain included.

Cross-platform named-pipe framing and ownership evidence does **not** establish Win32 ACL behavior, non-elevated Docker Desktop/WSL2 access, Windows daemon restart behavior or real daemon event/snapshot convergence. Those need Windows runtime evidence. Production platform support remains local Windows named pipes; the internal cross-platform fixture override is test-only. [DesktopSession container reconciliation](container-reconciliation.md) now owns subscription/recovery, bounded invalidation and authoritative snapshot integration, with separate deterministic presentation evidence and the current expanded test result.
