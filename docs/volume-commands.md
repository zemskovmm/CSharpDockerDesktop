# Borrowed volume deletion capability

The retained negotiated connection supplies Application's `IVolumeCommands` alongside volume/dependency reads, container/image commands, events and Logs. `DeleteVolumeAsync(name, cancellationToken)` asynchronously requests ordinary non-force deletion of one complete original volume name. Immutable Domain outcomes have no HTTP or Uno dependency. Browsing and inspection do not invoke this mutation. Session dependency prechecks, data-loss confirmation, operation reconciliation and deletion UI remain subsequent work.

Every supported API **1.40–1.56** defines `DELETE /volumes/{name}` with a required name, optional boolean `force` defaulting to false, HTTP 204 without a response schema, and JSON `message` errors at 404, 409 and 500. The capability explicitly sends `DELETE /v<negotiated>/volumes/<escaped-original-name>?force=false`. It reuses the existing volume Inspect name validation: reject absent/blank, over-4096-character, dot/dot-dot, control-character and malformed UTF-16 names; preserve all other accepted characters exactly, including plugin/cluster names, spaces, slashes, percent signs and Unicode. The local driver's volume-creation grammar is not imposed. The unchanged accepted name is escaped as one path component, preventing query or path injection. There is no force option, dependent-container removal, conflict escalation, prune request, replacement connection or automatic mutation replay.

## Protocol outcomes and reconciliation

| Disposition | Evidence |
| --- | --- |
| NotDispatched | Local validation, caller cancellation, disposed/stale owner or full command capacity prevented entering HTTP dispatch. |
| Acknowledged | HTTP 204 arrived on the retained transport before cancellation, deadline, disposal or continuity invalidation. |
| DaemonResponse | A complete HTTP rejection or unexpected status arrived; status and bounded error evidence are retained. |
| Uncertain | Dispatch may have happened but transport loss, cancellation, deadline, disposal or continuity change prevented a trusted completed outcome. |

Entering `HttpClient.SendAsync`, including its internal queue, is the conservative possible-dispatch boundary. Only HTTP 204 is acknowledged. **Acknowledgement alone never establishes authoritative volume absence or causality.** `RequiresReconciliation` is true for every possibly dispatched call, including acknowledgement, not-found, dependency conflict and other daemon responses. A lost response is not permission to replay deletion. Subsequent operation coordination must obtain fresh authoritative volume state, accounting for concurrent external changes and connection identity.

404 is NotFound (the official contract includes a missing volume or driver); 409 is dependency Conflict; 401/403 and operating-system permission errors are AccessDenied; other 4xx are InvalidRequest; 5xx are DaemonFailure; other statuses, including other 2xx and redirects, are UnexpectedResponse. TransportFailure, Deadline, ConnectionDisposed, StaleConnection and CapacityExceeded remain distinct. A response interrupted while reading its error body is Uncertain with its already received HTTP status retained. Error-body overflow does not erase an explicit daemon status or turn a conflict into an acknowledgement.

`DaemonMessage` preserves the original decoded JSON `message` string, or plain non-JSON error text. `DaemonErrorBody` additionally preserves the complete bounded original UTF-8 error body, including unknown JSON fields or JSON without a recognizable message. Empty completed bodies remain available empty strings. Oversized or interrupted bodies set `ErrorBodyUnavailable=true` and do not expose a misleading partial body; a completed body without a recognizable message has that flag false. Routine descriptions contain neither the name nor original daemon content. Neither original field is logged automatically; later UI must deliberately reveal sensitive daemon evidence.

Caller cancellation throws `VolumeCommandCanceledException`, an ordinary `OperationCanceledException` carrying the caller token and immutable `Outcome`. The outcome retains no-dispatch versus possible-dispatch, available status, and any completely acquired bounded error body/message. Cancellation at error-body EOF retains the completed evidence while remaining Uncertain. Cancellation is normal termination and never implies rollback.

## Lifetime, transport and bounds

Volume deletion shares the existing finite `MaximumConcurrentCommands` admission gate with both container and image mutations. Occupied capacity returns NotDispatched immediately. The existing `CommandTimeout` (30-second default) bounds the entire admitted command, independently of resource GET and long-lived stream deadlines. Error bodies reuse `MaximumCommandErrorBytes` (64 KiB default, configurable 64 bytes–1 MiB); unknown-length bodies consume at most budget plus one byte. Bounded JSON decoding runs off the caller thread.

The command borrows the sealed retained ordinary HTTP transport and negotiated version. HTTP/1.1 is explicit, and the transport disables redirects and implicit physical replacement after negotiation. A replacement attempt invalidates the generation and requires explicit fresh negotiation before later reconciliation. See [shared mutation transport protections](container-commands.md#transport-replay-and-lifetime). Linked caller/owner/deadline/continuity cancellation and final publication checks prevent a late non-cooperative success response from publishing a trusted acknowledgement. Requests, responses, error streams and admission are released on every terminal path. Calls never dispose the borrowed connection, events, Logs or unrelated capabilities.

Reviewed on 2026-10-14 against all 17 official definitions from [Docker API 1.40](https://docs.docker.com/reference/api/engine/version/v1.40.yaml) through [API 1.56](https://docs.docker.com/reference/api/engine/version/v1.56.yaml). [Selected source evidence](../tests/CSharpDockerDesktop.Connection.Tests/Fixtures/VolumeCommands/contract-evidence.json) records each original source URL/SHA-256, parameters, response contracts and ErrorResponse schema. All versions declare the same endpoint, non-force default and 204/404/409/500 contracts. This is source-derived evidence; fixture bodies are synthetic, not daemon captures.

The deterministic harness covers every version's declared statuses and negotiated endpoint; exact original-name encoding and invalid names; non-force requests without escalation; access denial, other 4xx/5xx and unexpected statuses; fragmented and exact/oversized known/unknown-length error bodies; raw original errors; cancellation before dispatch, after dispatch and at error-body EOF; transport loss after headers; deadlines, disposal and generation changes; late successful responses; and shared admission in both directions with container and image mutations. Controlled named pipes use actual `SocketsHttpHandler` to exercise lost responses, refusal of replacement/replay, explicit fresh negotiation followed only by authoritative reads, and issued cancellation/deadline/disposal cleanup. The simultaneous three-pool fixture deletes a volume while events and Logs stay active, then continues resource reads, container commands and liveness without additional negotiation.

On macOS 26.7.1 with .NET SDK 10.0.402, the complete harness passes **214/214 groups** and the Release solution build succeeds with zero warnings/errors. These are simulated protocol and controlled named-pipe results. They do not establish real Windows Docker Desktop/WSL2, non-elevated Windows ACL behavior, plugin/cluster compatibility, real running/stopped dependency conflicts, daemon restart or release performance evidence. Those real-host checks remain outstanding.
