# Borrowed image deletion capability

The negotiated connection now supplies Application's `IImageCommands` alongside image/container reads, container commands, events and Logs. `DeleteImageAsync(reference, cancellationToken)` removes one image ID or repository reference asynchronously. Domain outcomes contain no HTTP or Uno dependencies. DesktopSession operation coordination, confirmation and Images presentation integration remain subsequent work; this protocol capability does not dispatch from browsing or inspection.

Every supported API **1.40–1.56** uses `DELETE /v<negotiated>/images/<escaped-reference>?force=false&noprune=false`. The client reuses image Inspect's bounded ASCII distribution-reference validation, accepting IDs/prefixes, names, registry/port references, tags and digests. Invalid input is rejected locally; the validated original reference is escaped as one path segment. There is no force parameter in the capability, no dependent-container removal, conflict escalation, command replay, implicit handshake or replacement transport. It shares the existing finite command admission gate with container commands and the sealed retained ordinary HTTP pool. See [transport continuity/replay protection](container-commands.md#transport-replay-and-lifetime).

## Identity and removal evidence

A tag identifies a reference to image data. Removing one of several tags may only untag that reference while the image remains under another tag. Removing the last reference can remove image data, subject to daemon dependencies. ID deletion targets image data and can conflict when other references or containers protect it. Digest references are also daemon-managed aliases. These distinctions are documented by [Docker's image removal examples](https://docs.docker.com/reference/cli/docker/image/rm/); input validation does not infer the daemon's resolution, existence or safety decision.

`noprune=false` explicitly retains the API's default: eligible untagged parent images can also be removed. Multiple `Deleted` records may therefore include parents, rather than each record describing the requested image. The capability exposes no parent-preservation or platform selector; the optional API 1.50+ `platforms` query is omitted, retaining ordinary daemon image deletion behavior. Confirmation added in subsequent work must account for these consequences.

Only HTTP 200 with a decoded JSON array is acknowledged. Each meaningful removal object retains its original `Untagged` and/or `Deleted` strings in order, including repeated records; unknown additive fields beside recognized evidence are tolerated. An empty array is a valid acknowledgement with no removal evidence. An empty body, malformed JSON, wrong known-field types, empty/duplicate known fields, non-object entries or objects without recognized evidence are UnexpectedResponse; completed records before a later semantically malformed entry remain available. Returned records are read-only. **Acknowledgement, untagging and a `Deleted` record never independently prove the requested identity is absent.** All possibly dispatched calls require an authoritative image list/inspection, accounting for aliases and concurrent external changes.

## Outcomes, cancellation and budgets

| Disposition | Evidence |
| --- | --- |
| NotDispatched | Validation, capacity, disposal, stale connection or caller cancellation prevented entering HTTP dispatch. |
| Acknowledged | A complete, bounded, well-formed removal response arrived on the retained connection. |
| DaemonResponse | An explicit rejection or malformed/unexpected response arrived; its status is retained. |
| Uncertain | Dispatch may have happened, but interruption, cancellation, deadline, disposal or continuity loss prevented a trusted completed outcome. |

The conservative dispatch boundary is entering `HttpClient.SendAsync`, including its internal queue. `RequiresReconciliation` is true for every disposition except NotDispatched, including daemon rejections. A response lost after application must never cause blind replay. Caller cancellation throws `ImageCommandCanceledException`, an ordinary `OperationCanceledException`, with `Outcome` preserving possible dispatch, available HTTP status/message and any completed removal records. Cancellation during successful response decoding keeps uncertainty rather than promising rollback. An interrupted or incomplete body has `ResponseBodyUnavailable=true`; a completed error body may be available even when it contains no recognizable JSON message.

404 is NotFound; 409 is dependency/reference Conflict; 401/403 and operating-system access denial are AccessDenied; other 4xx are InvalidRequest; 5xx are DaemonFailure. Unsupported statuses and malformed/oversized HTTP 200 responses are UnexpectedResponse. TransportFailure, Deadline, ConnectionDisposed, StaleConnection and CapacityExceeded remain distinct. Complete bounded JSON `message` strings or plain non-JSON error text are preserved verbatim for deliberate display. Routine failure descriptions omit resource identifiers and daemon content. Nothing is automatically logged.

The existing finite CommandTimeout applies (30 seconds by default), independently of read and stream deadlines. `MaximumImageCommandResponseBytes` bounds successful removal bodies at 64 KiB by default (configurable 64 bytes–1 MiB); error bodies use `MaximumCommandErrorBytes` with the same default/range. Unknown-length bodies consume at most budget plus one byte. JSON parsing runs off the caller thread, has a bounded input and depth, checks cancellation through record projection, and retains completed records if later projection is interrupted. Linked caller/owner/deadline/continuity cancellation fences publication even for late cancellation-ignoring transport completions. Requests, responses, streams and admission are released on every termination; borrowed calls never dispose the retained owner.
