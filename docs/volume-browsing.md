# Application volume browsing

`DesktopSession` implements `IVolumeBrowser` using the borrowed `IVolumeReader` on its retained negotiated connection. Initial connection and every replacement/reconnect start a fresh volume list without another connection or negotiation. A missing reader produces Unavailable list/detail state. Snapshots stay in memory and are discarded on connection loss, replacement, disconnect or disposal. This boundary is read-only; volume events, presentation, dependency acquisition and deletion remain separate work.

Consumers read `VolumeSnapshot` after `VolumesChanged`, which may arrive off the UI thread. The snapshot carries the connection generation, complete selected name, immutable useful rows, exact latest accepted listing, list/detail states, inspection metadata and exact `RawJson`, and separate classified list/detail failures. Names use ordinal identity without normalization, prefix matching or shortening. Rows are deduplicated by that identity. Labels, rows and warnings are defensively copied into read-only collections, including results supplied by mutable capability implementations. Null metadata/labels remain unavailable; empty metadata and collections remain available empty values. Raw inspection and original daemon messages remain sensitive data and are never automatically logged or transmitted.

## Listing evidence and retained data

`Volumes` is the useful browsing collection. `LatestListing` is the exact most recent accepted successful read, with original collection order and warnings; it is not rewritten to match retained rows or an Inspect NotFound result. `Warnings` projects its warnings without changing null, empty, ordering, duplicates, whitespace or content. `Completeness`, `HasRetainedRows` and `IsAuthoritative` distinguish current complete state from incomplete or stale evidence. Ready describes completion of an available list read and is insufficient by itself to establish completeness.

| Read outcome | State / completeness | Useful rows and selection |
| --- | --- | --- |
| Non-null Volumes, no warnings (null or empty Warnings) | Ready / Complete; IsAuthoritative | Replace useful rows. Preserve selected complete name if present; otherwise clear selection and raw details. An empty collection is authoritative successful emptiness. |
| Non-null Volumes and one or more warnings | Ready / Incomplete; HasWarnings | Update/add returned names, retain previous names omitted from the response. Retained names set HasRetainedRows. Even an empty warning-bearing collection is not authoritative absence. Preserve selection and useful details. |
| Null Volumes, with any warning representation | Unavailable / Unavailable | Retain useful rows and selection; mark retained rows. Preserve the null collection and exact warnings in LatestListing. Never infer absence. |
| Refresh pending | Loading / Unavailable | Retain useful rows, previous listing/warnings and valid selection; mark retained rows. Previous completed inspection can remain useful. Fence an active inspection and reload it only if still requested. |
| Non-transport read failure | Failed / Unavailable | Retain useful rows, selection and latest accepted listing/warnings; mark retained rows. Preserve the original classified failure, HTTP status and daemon message separately from its safe description. No reconnection. |
| Shared connection invalidation | Unavailable / Unavailable | Clear rows, listing/warnings, selection and raw detail. A fresh generation starts with no cached resource data. |

An initial null listing has no useful rows but still differs from an authoritative empty listing. Partial responses never accumulate warning history: a new accepted successful listing replaces the warning collection exactly, including null and empty. Pending refresh and failure retain the latest accepted warnings because no newer listing has established replacement evidence.

Selection admits only a complete name in current usable rows, including explicitly retained rows under incomplete evidence. Invalid or null selection clears detail; selecting the same identity preserves existing or explicitly cleared detail. Selection changes, explicit inspection refresh and clearing increment the detail revision, cancel/supersede old detail work and immediately clear exposed raw JSON. Clearing retains the selected name and NotRequested state; list refresh does not reopen explicitly cleared inspection. A current successful inspection must return the exact selected name; a different identity becomes MalformedData and its raw data is never attached to the selection. A current Inspect NotFound removes that useful row, clears selection/raw detail and retains its classified failure. Superseded NotFound cannot remove newer state.

## Scheduling, recovery and lifetime

The Application coordinator has one volume worker, a capacity-one wake-up channel and one pending flag per list/detail family. Reads are serialized; repeated requests coalesce. When both families are pending, successive turns alternate so refresh bursts and selection bursts cannot monopolize the worker. List refresh supersedes earlier list and detail publications; selection changes supersede detail without canceling active list I/O. Requests run asynchronously with an explicit deadline and cancellation. A separate deadline remains active when a superseded reader ignores cancellation.

Connection identity, list/detail revisions, selected name, cancellation and deadline state fence both successful and failed publications. A volume transport-loss response or deadline clears all shared resource state and cancels Containers, Images, events, lifecycle/image commands and relevant Logs. It signals the existing connection owner; volume browsing has no reconnect loop. Loss originating from each of those shared capabilities or liveness also invalidates volume state and notifies its observers. Shared connection identity is fenced before cancellation callbacks run. Image-command transport-loss notification now reaches every browser immediately.

Replacement, disconnect and disposal invalidate publication before cancellation and asynchronously join all owned volume work before releasing the retained connection. A non-cooperative reader must finish before connection disposal or recovery can obtain a replacement. Its deadline still makes exposed state unavailable promptly while the join is pending. Repeated disconnect/disposal calls join the same owned work; shutdown does not create overlapping connections or resurrect late raw data. Slow I/O does not synchronously block the UI. Observer exceptions do not orphan volume work and are not logged.

Twelve added deterministic volume browsing groups exercise initial/reconnect state, missing capability, null versus empty collections/warnings/metadata, warning-bearing rows and empty lists, retained rows and incomplete-list disappearance safety, exact sensitive warning/raw data, defensive immutability, complete ordinal names, reorder/deduplication, returned-identity rejection, complete-list and Inspect NotFound disappearance, all classified non-transport failures/status/original messages, 1,000-request bursts, list/detail fairness and serialization, stale successful/failed list/detail publications, cooperative and non-cooperative deadlines (including superseded requests), retained-connection recovery, repeated disconnect/disposal and joined connection release.

All-capability fixtures keep Containers, Images, shared events, lifecycle and image commands, and active Logs present while volume work proceeds. They test shared loss from each owner plus liveness, disconnect and disposal with a delayed non-cooperative volume read. A volume deadline cancels every shared capability, joins the late read before connection release, and recovers fresh volume/container/image state plus Logs through the existing connection owner. Existing protocol fixtures and synthetic named-pipe tests remain separate evidence.

## Outstanding real validation

Controlled capabilities establish simulated scheduling, state, ownership and recovery behavior. They do not establish real Windows named-pipe ACLs, Docker Desktop/WSL2 volume behavior, daemon warning behavior, external volume events, Windows delivery, GUI volume interaction or workstation CPU/memory/latency targets. Real Windows/Docker checks remain outstanding. No graphical volume browser or volume mutation is delivered by this coordinator task.
