# Application image deletion coordination

`DesktopSession` implements `IImageOperations` alongside `IImageBrowser`. The caller supplies `ImageOperationRequest` with the complete authoritative image ID and the browsing connection generation. Confirmation belongs to the future Presentation integration. This boundary executes only `IImageCommands.DeleteImageAsync` using that captured ID: deletion is non-force, preserves the daemon's ordinary eligible parent pruning, and never removes dependent containers, selects a tag, escalates a conflict, pulls or pushes an image.

`ExecuteImageOperationAsync` returns asynchronous completion. `ImageOperation` retains the latest immutable operation independently of selection and Inspect lifetime; one completed or unresolved operation remains available until another operation is admitted. `ImageOperationChanged` can originate off-thread. Consumers read the latest snapshot and marshal it for display; observer exceptions cannot orphan image work and are not logged. Notifications coalesce unchanged snapshots. Immutable snapshots are replaced under the session lock; retained removal collections are copied into read-only collections.

Admission has one slot and no operation queue. An identical pending request shares its completion. Excess concurrent requests, a canceled-before-dispatch caller, a stale generation, an absent/missing full identity, and missing connection/read/command capabilities return completed NotDispatched evidence without invoking a mutation. Rejected requests do not replace useful retained operation evidence. Full identity must match a current authoritative row; shortened IDs, names and tag lookups do not substitute for that match. The borrowed protocol capability also retains its existing shared container/image command admission budget.

## Command evidence and authoritative observations

The request, protocol disposition, original classified failure, HTTP status, original daemon message, response-body availability and ordered removal records remain in `CommandOutcome`. Observation evidence has independent connection generation, existence, classified read failure and attempt count. Original daemon/resource content is sensitive and never emitted to automatic diagnostics.

| Phase or resolution | Meaning |
| --- | --- |
| CommandPending | The admitted command is outstanding. Possible dispatch is conservatively recorded before capability invocation. |
| Reconciling | Session-owned authoritative image reads are establishing current state. |
| Completed / ObservedAbsent | A current full list excludes the captured target, or subsequent target Inspect reports NotFound. |
| Completed / ObservedPresent | A current full list and successful target Inspect establish continued existence. |
| Completed / NotDispatched | Classified evidence establishes no command dispatch. |
| Completed / Unresolved | Observation failed, was superseded beyond the bounded attempts, or connection/shutdown invalidated it. |

HTTP acknowledgement, empty removal arrays, untagging, target `Deleted` records and parent `Deleted` records never establish absence themselves. ObservedAbsent describes current Engine state and does not claim the delete caused it. A 409 dependency conflict remains available for deliberate display while authoritative reads establish current state; it never prompts force or repeated mutation. A daemon 404 is still reconciled, because command failure and observed absence are different evidence.

Every possibly dispatched result, including daemon rejection, caller cancellation and uncertain/lost responses, requires authoritative reconciliation. The existing single image read coordinator performs a full list and, when the target is present, a targeted Inspect regardless of current selection or whether details are closed. The full snapshot refresh accounts for eligible parent pruning and clears any disappeared selection/Inspect. Requested detail receives fair turns between observations and ordinary browsing work. A capacity-one signal, coalesced browsing flags and one pending observation retain bounded scheduling state; image reads never overlap one another.

Dispatch and response fences invalidate older list/detail revisions and clear exposed requested Inspect for all selected identities, including parents. Image events and manual refresh also fence operation observations. Obsolete successful reads cannot resolve an operation or resurrect Inspect. An observation interrupted by a newer image invalidation requires a bounded replacement. Caller navigation/selection only affects browsing detail, never cancellation of required operation observation.

## Cancellation, recovery and ownership

Caller cancellation prevents dispatch when possible. After capability invocation, `ImageCommandCanceledException.Outcome` preserves dispatch/response evidence; reconciliation uses the session lifetime, independent of the caller token. Unknown cancellation evidence remains conservative uncertainty. An independent command deadline continues to run when a command ignores caller cancellation. Read and command deadlines invalidate current publication and signal the existing shared connection recovery path. They do not create a second connection owner.

Transport loss retains an unresolved operation and joins the old generation before fresh negotiation. Reconnection can resume observation only when both the actual endpoint and a known, nonempty Engine ID match the original operation. A missing or unrelated Engine ID cannot resolve that operation. The original request retains its original browsing generation; a successful resumed observation records the newer observation generation. Recovery performs reads only and never replays deletion. Classified cancellation evidence can remain useful during automatic recovery without restoring browsing state or resolving the operation. An obsolete successful command completion is not accepted as current success.

Disconnect, replacement and disposal invalidate publication before canceling owned work. Image commands, observations and ordinary reads are joined alongside container operations, events and Logs before releasing the borrowed connection. A capability that ignores cancellation must return before that release; the asynchronous join keeps ownership correct while the shell remains responsive. Explicit shutdown rejects its late publications. Retention is one operation, admission is one command, and observations per connection workflow are bounded by `ImageOperationOptions.MaximumObservations` (default four). Command deadlines and follow-up intervals are separately configurable implementation defaults. Fresh same-Engine recovery may undertake a new bounded observation workflow; mutation remains single-dispatch.

## Verification and evidence limits

Twelve focused dependency-free harness groups cover acknowledged deletion and parent snapshot/selection refresh; conflicts and continued existence; empty, untag-only and parent-only records; missing targets and Inspect NotFound; stale, canceled and absent-capability admission; repeated excess concurrency and duplicate completion sharing; deselection/closed details; pre-dispatch, pre-response and event-obsolete read fences; caller cancellation and preserved classified evidence; applied-before-response-loss state after same-Engine recovery with no replay; unrelated/unknown Engine reconnect; bounded failed observations; command/read deadlines, including manual refresh and non-cooperative caller cancellation; joined retry/disconnect/disposal and late commands/list/Inspect; and coexistence with active container commands, container Inspect, shared events and Logs. These controlled capabilities simulate Engine state and failure timing; they are not captured real daemon behavior.

On 2026-10-14, the dependency-free harness passed **155/155 groups on macOS 26.7.1 with .NET SDK 10.0.402**. The Release solution build completed with zero warnings and errors. Real Windows non-elevated named-pipe access, Docker Desktop/WSL2 dependency/parent-pruning behavior, alternative Engine compatibility, Windows delivery and workstation performance evidence remain unavailable on this macOS host. Existing protocol fixtures and synthetic named-pipe evidence remain separate. Image confirmation and delete controls are subsequent Presentation work; the current Images page remains read-only.
