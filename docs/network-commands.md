# Borrowed network deletion protocol

The retained negotiated connection supplies Application's `INetworkCommands` alongside `INetworkReader`, other resource reads and commands, events, Logs and liveness. `DeleteNetworkAsync(id, cancellationToken)` requests ordinary deletion of one complete original daemon network ID. Domain outcomes and cancellation evidence are immutable and independent of HTTP and Uno. The capability borrows the owner's transport, negotiated version, shared mutation admission and lifetime; it creates no handshake, subscription, replacement connection or automatic retry.

This capability sits below deletion eligibility and confirmation. A caller must supply the full original daemon ID, never a name, prefix or display identity. Syntax validation cannot prove completeness because the Docker contract also accepts names and does not prescribe an ID width. List and Inspect observations do not authorize deletion. Built-in bridge/host/none protection, fresh attachment/dependency preparation, default blocking while attachments remain, user confirmation and session-owned reconciliation remain subsequent Application/presentation work. Browsing never invokes deletion, and this change wires no destructive UI action.

## Endpoint and original identity

All supported APIs **1.40–1.56** declare `DELETE /networks/{id}` with one required string path parameter and no force parameter. The actual request is `DELETE /v<negotiated>/networks/<escaped-original-id>` with no query or body. The shared network identity validation rejects absent/blank IDs, exact dot segments, controls, malformed UTF-16 and IDs longer than 4096 UTF-16 code units. Accepted IDs are preserved without trimming, shortening, normalizing or unescaping and encoded with `Uri.EscapeDataString` as one path component. This covers local hexadecimal IDs, swarm IDs, Unicode and opaque driver IDs, including slashes, backslashes, percent signs and query/fragment punctuation. There is no fixed hexadecimal-width requirement, name lookup, force bypass, prune request or attached-container removal.

The official definitions declare 204 without a response schema, and 403/404/500 with `ErrorResponse.message`. Every version lists 403 as the rejection for predefined networks. API-version mismatches and other 4xx remain invalid requests. An HTTP 409 response is preserved as Conflict even though these endpoint OpenAPI definitions do not list it.

Moby's implementation also uses **403 for dependency failures**: `ActiveEndpointsError` is Forbidden and formats `network <name> id <id> has active endpoints`. This appears in the [19.03 vendored implementation](https://github.com/moby/moby/blob/v19.03.0/vendor/github.com/docker/libnetwork/error.go) and [28.0 implementation](https://github.com/moby/moby/blob/v28.0.0/libnetwork/error.go). [Network deletion](https://github.com/moby/moby/blob/v28.0.0/daemon/network.go) may prefix it with `error while removing network: `. [Configuration-only network dependencies](https://github.com/moby/moby/blob/v28.0.0/libnetwork/network.go) use `configuration network "<name>" is in use`. [The HTTP status mapper](https://github.com/moby/moby/blob/v28.0.0/api/server/httpstatus/status.go) maps Forbidden to 403 and Conflict to 409.

The client recognizes these specific dependency message forms, requiring the complete requested ID in the active-endpoint form, and classifies them as Conflict while preserving HTTP 403 and the unchanged original body/message. Docker exposes no structured reason code in this endpoint's error schema; recognizing these source-established forms is an interpretation of available evidence. Unrecognized 403 responses remain AccessDenied, including authorization and daemon policy denials; unfamiliar driver/localized formats remain available in their original body rather than being guessed from generic keywords. This protocol classification neither performs an eligibility check nor authorizes a retry.

## Outcomes, original errors and reconciliation

| Disposition | Evidence |
| --- | --- |
| NotDispatched | Validation, cancellation, disposed/stale connection or occupied shared command capacity prevented entering HTTP dispatch. |
| Acknowledged | HTTP 204 arrived before caller/owner cancellation, deadline or continuity invalidation. |
| DaemonResponse | An HTTP rejection or unexpected status arrived, with completed bounded body evidence or explicit overflow evidence. |
| Uncertain | A possibly dispatched request was interrupted by cancellation, transport failure, deadline, disposal or continuity replacement. Available headers/body evidence survive. |

Entering `HttpClient.SendAsync`, including internal queueing, is the conservative possible-dispatch boundary. Only 204 is an acknowledgement; other 2xx, redirects and unrecognized statuses are UnexpectedResponse. **Acknowledgement does not establish authoritative absence or causality.** `RequiresReconciliation` is true for every possibly dispatched call, including acknowledged, missing, denied and conflict outcomes. Subsequent Application coordination must obtain fresh authoritative network state. An interruption, daemon conflict or transport replacement never triggers automatic mutation replay.

404 is NotFound; 409 and recognized 403 dependency forms are Conflict; other 401/403 and operating-system permission errors are AccessDenied; other 4xx are InvalidRequest; 5xx are DaemonFailure. TransportFailure, Deadline, ConnectionDisposed, StaleConnection and CapacityExceeded remain distinct. Already received HTTP status survives error-body failure, cancellation and late transport invalidation.

`DaemonMessage` retains the original decoded JSON message, or the original non-JSON text. `DaemonErrorBody` retains the complete bounded original decoded UTF-8 body, including unknown fields and valid JSON without a message. Empty completed bodies are available empty strings. Oversized, truncated or interrupted bodies set `ErrorBodyUnavailable`; no partial body is presented as complete. Oversize preserves the daemon-response status/classification, while an interrupted/truncated body returns Uncertain. A premature EOF against Content-Length is an interruption even for a controlled transport that does not throw itself. Malformed but complete JSON remains original body evidence. Invalid UTF-8 sets ErrorBodyUnavailable instead of presenting replacement characters as original evidence. Routine descriptions contain neither target IDs nor private daemon content; neither original field is automatically logged or transmitted.

Caller cancellation throws `NetworkCommandCanceledException`, an ordinary `OperationCanceledException` with the original caller token and immutable `Outcome`. Cancellation before dispatch carries NotDispatched; cancellation after possible dispatch carries Uncertain, any received status and any completely acquired bounded original body/message. Cancellation at error-body EOF retains complete evidence. Cancellation never implies rollback.

## Lifetime, bounds and transport continuity

Network commands share `MaximumConcurrentCommands` with container, image and volume mutations. Occupied capacity returns NotDispatched immediately; every termination releases admission. `CommandTimeout` bounds an admitted request (30 seconds by default), independently of resource read and stream-opening deadlines. `MaximumCommandErrorBytes` bounds error retention (64 KiB default, configurable 64 bytes–1 MiB); unknown-length reads consume at most the budget plus one byte. Bounded body decoding runs off the caller thread.

The existing sealed ordinary connection uses exact HTTP/1.1 and refuses replacement physical pipes after negotiation, before a replacement can carry the mutation. The command subscribes to generation invalidation, links caller/owner/deadline/continuity cancellation and fences final publication. Late responses cannot publish an acknowledgement after invalidation. Requests, responses, streams and admission are released; borrowed calls do not dispose the connection, events or Logs. See [shared transport replay safeguards](container-commands.md#transport-replay-and-lifetime).

## Evidence and verification limits

Reviewed on 2026-10-15 against all 17 official definitions from [API 1.40](https://docs.docker.com/reference/api/engine/version/v1.40.yaml) through [API 1.56](https://docs.docker.com/reference/api/engine/version/v1.56.yaml). [Selected contract evidence](../tests/CSharpDockerDesktop.Connection.Tests/Fixtures/NetworkCommands/contract-evidence.json) records original source URLs/SHA-256 values, endpoint parameters, declared responses, error schema and supplemental Moby implementation evidence. These are retrieved authoritative contracts; fixture responses are synthetic, not captured daemon data.

Seven focused protocol groups cover every negotiated version's endpoint and declared status; exact opaque IDs/encoding and invalid targets without dispatch; acknowledgements, missing/conflict/denial/invalid/daemon/unexpected responses; complete, fragmented, malformed, exact-budget, oversized, truncated and lost error bodies; cancellation before/after dispatch and at EOF; lost responses, deadlines, disposal, continuity invalidation, late non-cooperative completion and shared admission with every existing command family in both directions. Controlled named pipes exercise actual SocketsHttpHandler, applied-command response loss, refusal to open/replay onto a replacement, explicit fresh negotiation followed only by authoritative network reads, and issued cancellation/deadline/disposal cleanup.

The simultaneous three-pool named-pipe fixture deletes a network while events and Logs remain open, then continues network/container/image/volume reads, other commands and liveness. Closing subscriptions leaves the ordinary transport usable. Exactly three initial handshakes serve these ordinary/event/Logs pools; network deletion adds none.

These are simulated protocol and controlled named-pipe checks. They do not establish real Windows Docker Desktop/WSL2 behavior, non-elevated Windows ACLs, real built-in/attached/configuration-only/swarm network conflicts, daemon restart compatibility or workstation performance. Those real-host checks remain outstanding.

On 2026-10-15, using .NET SDK 10.0.402 on macOS 26.7.1, the final complete executable harness passed **305/305 groups**, including all seven network-deletion groups and the simultaneous events/Logs/read/command fixture. The full Release solution build passed with **zero warnings and zero errors**. Repeated verification also exposed intermittent existing session-test timing issues: one run timed out in `NetworkActorIdentityAndConservativeDetail` waiting for its synthetic event clock, and another stalled in the existing container-reconciliation portion. The subsequent complete confirmation run passed; those unrelated session/test implementations were not changed by this protocol task.
