# Container Stats acquisition and derivation

A negotiated connection exposes Application `IContainerStatsSource`. `SubscribeStatsAsync` requires the exact full container ID already obtained by inspection/listing. It performs an authoritative Inspect on its independent transport and requires `Inspect.Id` to equal that ID. It never resolves a name or prefix into another target. Invalid bounded identities fail before transport allocation; inspection disappearance remains `NotFound`.

This capability acquires raw counters only. The independent calculator described below derives immutable measurements. DesktopSession metrics/history ownership, active-view selection, approximately one-Hz display, five-minute retention, charts and Stats UI remain subsequent work. There is no continuous stream per table row and no automatic reconnect/replay here.

## Ownership and negotiated transport

The capability borrows the selected connection. The caller owns `IContainerStatsSubscription.DisposeAsync`; disposing it leaves the selected connection usable. Connection disposal cancels and joins every Stats producer along with existing streams. Each Stats subscription owns a separately negotiated HTTP/pipe pool, following events/logs. Admission is separate from log/command admission; ordinary reads, commands and liveness retain their original sealed connection without renegotiation.

Before requesting/publishing Stats, the new pool validates the selected endpoint, a nonempty matching Engine ID, Engine version, platform metadata, complete API compatibility and transport generation. It requests `GET /v{negotiated}/containers/{escaped-full-id}/stats?stream=true`. It deliberately omits `one-shot`: API 1.40 has no such option, and later contracts restrict it to `stream=false`. A returned sample ID/platform, when supplied, must agree with the selected identity/platform. Missing sample IDs remain associated with the ID established by Inspect; missing platform evidence stays unknown when connection metadata also lacks it.

Opening includes negotiation, Inspect and response headers/body acquisition under a dedicated deadline. The ordinary short request deadline still bounds each handshake request, but neither that deadline nor the opening deadline limits a healthy established stream. A stalled/empty established body waits for explicit cancellation; it emits no invented samples or heartbeat measurements. Consumer cancellation of one channel read does not end the subscription: cancel the opening token or dispose the subscription.

## Raw evidence

Domain records and immutable maps/arrays preserve unsigned 64-bit counter precision, null/unavailable versus zero, and missing versus observed-empty collections. They retain current and previous CPU total/system counters, online/per-core CPU evidence, user/kernel counters, Windows processor count, read/preread timestamps, Linux memory usage/limit/cache/cgroup evidence, Windows commit/private working set, per-interface network counters and per-device/per-operation byte counters. Windows storage read/write byte/count counters remain separate from Linux Block I/O. No counter is converted through floating point, aggregated, or called filesystem disk-space usage.

Timestamps retain original RFC3339 text, signed Unix seconds and nanoseconds without fractional DateTime rounding. Missing/empty timestamps are unavailable. A daemon's year-one zero timestamp is preserved as historical raw evidence; it is not a current measurement. CPU totals have nanosecond units on Linux and 100ns units on Windows. Absent Linux system/per-core/memory/Block I/O evidence is not manufactured for Windows; Windows memory percentage/limit cannot be inferred from private working set.

All bounded `memory_stats.stats` keys are retained, including `cache`, `total_inactive_file` and `inactive_file`. These support Docker CLI cache-adjusted derivation for historical cache evidence, cgroup v1 and cgroup v2. The Engine reference's illustrative formula uses `cache` for v1; current Docker CLI uses `total_inactive_file`, with `cache` used by Docker 19.03 and older. Acquisition makes no formula choice. See the [official CLI explanation](https://docs.docker.com/reference/cli/docker/container/stats/) and [CLI helpers](https://github.com/docker/cli/blob/v28.0.0/cli/command/container/stats_helpers.go).

## Completion, privacy and bounds

Read `Samples` until it ends, then inspect `Completion`. Completion occurs after the HTTP response and dedicated pool are closed. `CleanEnd` retains legitimate queued final samples; natural pool disposal does not invalidate its negotiated generation. `Canceled` covers caller token, subscription or owner disposal. `Failed` reports malformed samples, transport loss and other classified failures. Malformed/truncated tails retain already validated earlier samples with a failed completion; an incomplete final sample is never published. Transport loss, cancellation/disposal and supersession suppress queued output, including a read crossing cleanup. Generation is checked after callback detachment and on both sides of dequeue/availability, preserving the event/log cleanup-race fix. A change after completed cleanup suppresses later delivery without rewriting the historical completion result.

Failures distinguish `NotFound`, `AccessDenied`, `InvalidRequest`, `IncompatibleApi`, `DaemonError`, `MalformedSample`, `OpeningDeadline`, `TransportLoss` and `SubscriptionLimit`. Bounded original HTTP daemon content and status are deliberate caller data, with a truncation flag; descriptions contain no raw daemon payload. This feature adds no automatic logging or telemetry.

Default implementation tuning, validated with finite upper limits in `DockerConnectionOptions`:

| Allocation | Default |
| --- | --- |
| Concurrent Stats subscriptions per selected connection, including opening/completed subscriptions until disposal | 2 |
| Whole opening deadline | 10 seconds |
| Buffered samples per subscription | 8 |
| Individual JSON object | 256 KiB |
| Total retained collection entries per sample, across both per-CPU arrays, memory keys, interfaces and I/O entries | 1,024 |
| HTTP daemon error prefix | 16 KiB |
| JSON nesting depth / decoder read buffer | 64 / 4 KiB |
| Inspect response / exact identity length | shared 1 MiB / 4,096 characters |

A bounded `Channel<T>` waits when full. At most one decoded sample is pending delivery in addition to the channel, one bounded JSON object and the fixed read buffer; it does not accumulate read-ahead samples. Cancellation interrupts opening, reading and blocked delivery. Disposal joins the producer and transport, including a late response from a controlled noncooperative transport. Admission stays reserved until disposal even at clean EOF, bounding retained completed channels as well.

The incremental object framer accepts fragmented and consecutive JSON objects without requiring line separators. System.Text.Json validates syntax and a strict UTF-8 pass validates even unknown text fields. Unknown additive fields are tolerated inside the byte/depth bounds. Known fields with malformed types, invalid counters/timestamps, collection excess, oversized samples or partial JSON at clean EOF fail explicitly. EOF between complete objects (with optional whitespace) is clean. I/O exceptions are transport loss; no reconnect is attempted.

## Schema sources and stopped/paused containers

All seventeen [official OpenAPI documents from 1.40](https://docs.docker.com/reference/api/engine/version/v1.40.yaml) through [1.56](https://docs.docker.com/reference/api/engine/version/v1.56.yaml) were inspected. `Fixtures/Stats/contract-evidence.json` records each URL, SHA-256, request parameters, response statuses, response schema and typed root fields. The response is generic-object with examples through 1.47; typed Stats definitions start at 1.48; `os_type` appears at 1.52. `stream=true` is common across the full range. Platform fields also exist in [Moby's API-1.40-era types](https://github.com/moby/moby/blob/v19.03.0/api/types/stats.go). Independent synthetic Linux/cgroup and Windows fixtures follow these official examples/types rather than production serialization.

The CLI documentation describes live data for running containers and says stopped containers do not return data. The protocol must also tolerate Engine implementations returning empty/zero-date structures: [old collection code](https://github.com/moby/moby/blob/v19.03.0/daemon/stats/collector.go) publishes identity-only evidence for stopped/missing tasks, while [current daemon Stats code](https://github.com/moby/moby/blob/v28.0.0/daemon/stats.go) returns empty evidence for unavailable tasks and cleanly ends when collection closes. Neither absence nor zeros establish a running container. The Stats API specifies no separate paused-container status or guarantee of fresh advancing counters. The [Linux task collector](https://github.com/moby/moby/blob/v28.0.0/daemon/stats_unix.go) and [Windows HCS collector](https://github.com/moby/moby/blob/v28.0.0/daemon/stats_windows.go) obtain platform task counters; paused behavior can therefore stall or retain unchanged counters. This is an inference from the collection paths, not a promised paused-stream behavior. Future coordination must reconcile authoritative lifecycle state and freshness before presenting current measurements, especially on stop/pause. Acquisition neither rejects a paused container based on a guessed rule nor synthesizes activity.

## Verification and remaining limits

The dependency-free harness covers every negotiated API version; cgroup v1/v2 and Windows availability; missing/zero/empty/null evidence; unsigned maximum counters; additive fields; exact timestamps; one-byte/random fragmentation; consecutive objects; malformed types/UTF-8, truncation, sample/depth/collection limits; slow-consumer backpressure; admission; opening/read/blocked-delivery cancellation; clean EOF draining; owner/stream generation changes; and joined disposal. The existing gated cleanup tests now exercise Stats for dequeue/availability races before and after cleanup, including replacement after callback detachment without consumer participation.

Controlled named-pipe HTTP uses four independent pools with Stats, logs and events open together while all resource families, mutations, dependency requests and liveness run on the selected ordinary connection. Request counts establish four handshakes total and one request per live stream. This tests actual SocketsHttpHandler framing, escaped negotiated requests and transport cleanup on the local test host; it is not a real Docker daemon.

Real Windows named-pipe permissions and Engine restart, Docker Desktop WSL2, Windows process/Hyper-V isolation, running/stopped/paused lifecycle behavior, live cgroup variants, long-duration memory/CPU profiles and comparison of derived values against a live Docker CLI still require real Windows/Docker runs. No Stats UI or graphical verification is claimed by this acquisition task.


## Reusable calculation boundary

Domain `ContainerStatsMeasurements` contains immutable independent measurements: CPU percent, exact unsigned memory usage bytes, memory percent, Windows commit bytes, network receive/send bytes per second and Block I/O read/write bytes per second. Every measurement has nullable `Value`, an explicit `Availability` reason and formula/evidence `Source`. `CpuBaseline` identifies embedded previous CPU evidence versus a previous delivered sample. Zero with `Available` is legitimate; null must never be rendered as zero. Provenance such as `LinuxRawAdjustmentRejected` must remain available to presentation so raw fallback is distinguishable from cache-adjusted usage. Results do not retain sample history or mutate raw acquisition evidence.

Application `ContainerStatsCalculator` is synchronous CPU-only arithmetic, independent of Uno, HTTP and stream ownership. One single consumer owns it and calls `Calculate(sample)`. It retains only the immediately preceding immutable sample. Work and temporary maps are proportional to the current/prior bounded sample collections, independently of viewing duration. The existing acquisition collection/byte limits bound those samples; the calculator adds no history or duration-dependent allocation. The caller must call `Reset()` on stream replacement, reconnection or any lost continuity, including same-ID/same-platform replacement. A fresh calculator is appropriate only for a genuinely new observation context whose embedded CPU interval is acceptable; use `Reset()` before its first calculation to prohibit that interval.

Every calculation replaces the baseline, including samples with missing/invalid fields. It never skips invalid samples to compare with older evidence. Container ID/platform changes invalidate all interval comparisons on that call. A fresh instance may use `PreviousCpu` and `PreRead` for its first CPU result; these never seed network/storage rates. Explicit reset suppresses embedded previous CPU evidence on the next call. Later calls use the preceding delivered sample exclusively, even when the sample carries different embedded CPU counters. Embedded Windows CPU assumes `NumberOfProcessors` applies across that embedded interval because the protocol supplies only one processor count. Delivered pairs require unchanged count evidence at both ends. Missing previous CPU/count evidence stays unavailable.

## CPU formulas and source versions

Formula evidence was reviewed against these precise official tags (not an assertion of the newest release): [Docker CLI v28.0.0 helpers](https://github.com/docker/cli/blob/v28.0.0/cli/command/container/stats_helpers.go), [Docker CLI v19.03.0 helpers](https://github.com/docker/cli/blob/v19.03.0/cli/command/container/stats_helpers.go), [Moby v28.0.0 Stats types](https://github.com/moby/moby/blob/v28.0.0/api/types/container/stats.go), [Moby v28.0.0 Windows collection](https://github.com/moby/moby/blob/v28.0.0/daemon/stats_windows.go) and [Moby v28.0.0 Linux collection](https://github.com/moby/moby/blob/v28.0.0/daemon/stats_unix.go). The acquisition schema evidence remains separately pinned to API 1.40–1.56.

Linux: `CPU% = (current total - prior total) / (current system - prior system) * CPUs * 100`. Counters are nanoseconds. Positive `OnlineCpus` is preferred; otherwise a nonempty per-CPU array supplies its length, as in the CLI. Per-core values themselves are not needed for count evidence. Both interval endpoints must supply the same applicable CPU count. Total delta zero is a valid zero when system delta is positive; absent fields, decreasing counters and nonpositive system denominator are unavailable. CPU percent may legitimately exceed 100 on Linux.

Windows: `CPU% = total-runtime-100ns delta / (floor(elapsed nanoseconds / 100) * NumberOfProcessors) * 100`. The collector maps HCS `TotalRuntime100ns` and supplies daemon processor count. Linux system counters and per-core fallback must not be substituted. Elapsed timestamps, total counters and positive processor count are required, with unchanged processor count for delivered pairs. Sub-100ns intervals have no valid denominator. Unknown platforms do not select a CPU, memory or I/O formula. Platform-independent network rates remain supported when both samples have identical platform evidence (including both unknown), matching container identity and complete byte/time/topology evidence.

Both formulas subtract exact integers before floating-point division. This deliberately avoids the CLI helper's floating-point Linux subtraction and unsigned reset hazards. The calculator also requires valid advancing timestamps for Linux interval evidence, a conservative freshness boundary beyond the CLI's arithmetic helper. This mathematical timestamp condition does not establish authoritative freshness.

## Memory semantics

Linux follows the modern CLI's ordered cache tests: use `usage - total_inactive_file` when that key is present, non-null and strictly below usage; otherwise try `usage - inactive_file` under the same condition. Thus usable cgroup-v1 evidence wins over cgroup-v2 evidence when both occur. If modern keys are present but their values are at or above usage and neither test succeeds, return raw usage with `LinuxRawAdjustmentRejected` provenance, matching the modern helper's raw fallback. Equality follows the CLI's strict comparison; zero usage remains a valid zero. Do not subtract historical cache after rejecting modern evidence.

Only when neither modern key exists does historical `cache` supply `usage - cache`, following the v19.03.0 helper. Historical cache equal to usage produces zero; cache above usage is unavailable instead of unsigned wrapping. Because raw records preserve availability more precisely than Go zero-value maps, null adjustment evidence is unavailable immediately, and absent/empty/unrelated stats without any adjustment key is unavailable. A missing key never implies a zero cache. These are deliberate conservative differences for incomplete synthetic/daemon evidence. No daemon-version or cgroup classification is guessed from unrelated fields.

Linux memory percent is `derived usage / limit * 100`. Missing limit and zero limit give distinct unavailable reasons; they do not invalidate supported usage bytes. Windows usage is private working set; commit bytes is a separate measurement, never a substitute. Windows memory percentage is unsupported even if Linux-looking usage/limit fields appear. Commit peak remains available in the raw record. Neither memory zeros nor any sample's availability establish running state.

## Rates, topology and invalidity

Elapsed time is computed directly from signed seconds and nanoseconds as an integer; fractional seconds are never rounded through `DateTime`. Missing timestamps, the daemon year-one zero date, invalid timestamp components, repeated dates and backward time make interval metrics unavailable. Memory measurements remain independently supported. A positive interval as small as one nanosecond is preserved. Network and I/O use `sum(per-contributor current - prior byte counters) * 1,000,000,000 / elapsed nanoseconds`, with all subtraction and aggregation in `BigInteger` before conversion to finite doubles. Aggregates may exceed `ulong.MaxValue`; a one-byte change near that maximum remains observable. No unsigned wrapping, negative rate, NaN or infinity is returned.

Network totals require observed collections at both endpoints, identical interface names and unchanged endpoint/instance IDs (including transitions between absent and reported identity). Null entries or missing directional bytes invalidate that direction. Any contributing decrease is a counter reset for that direction. A newly added, removed or renamed interface invalidates the interval total; no partial sum or assumed zero baseline is manufactured. Unreported replacement of an identically named interface with monotonic counters cannot be detected from the available evidence; callers must reset on known continuity loss.

Linux Block I/O matches complete case-insensitive `Read`/`Write` operations by `(major, minor)` separately for each direction. Missing device identity/value invalidates the affected direction; duplicate device/direction entries are ambiguous. `Total`, `Sync` and `Async` are overlapping summaries and are ignored. Unknown/absent operation names invalidate both directions, since their contribution cannot be classified. This is intentionally stricter than the CLI helper's first-character operation matching. A nonempty collection with no classified entry for a direction does not prove zero in that direction. Changed contributor sets invalidate that direction; missing write evidence does not invalidate complete read evidence. Windows uses separate storage read/write byte counters, never Linux device counters. Observed-empty collections at both ends prove zero activity; absent collections do not. Every such result describes I/O activity, not disk-space consumption.

Session coordination must gate results using authoritative container lifecycle, selected connection and freshness. The calculator does not infer stopped/running/paused state, perform reconnection, sample at a display cadence, retain history or publish UI updates.

## Calculation verification and limits

Four deterministic calculation groups cover Linux online/per-core count evidence and count changes; modern cgroup-v1/v2 precedence, historical cache, null/missing/invalid adjustment evidence; Windows 100ns rounding, processor requirements, private working set versus commit; exact nanosecond and subsecond intervals; valid zeros; first samples and explicit resets; identities/platform changes; unavailable or backward timestamps; directional partial fields; counter resets; interface/device topology and reported identity changes; duplicate/unknown/summary I/O operations; observed-empty collections; one-byte deltas near unsigned maximum and sums beyond that maximum. Independent decimal arithmetic supplies expected fixture values rather than calling production formulas. Thirty thousand calculations exercise repeated baseline replacement without accumulated history; this is structural/deterministic evidence, not a long-duration heap benchmark.

The existing negotiated acquisition fixtures now flow through the calculator for all API 1.40–1.56 Linux variants and Windows evidence. Two Linux samples use an exact half-second interval and unchanged counters to prove zero rates after actual acquisition; first CPU/memory measurements are checked against independent expected values. These fixtures and controlled transports are synthetic. No live Windows process/Hyper-V isolation, real cgroup or Docker CLI comparison was available on this macOS test host. Formula-source review plus deterministic mathematical/fixture checks do not claim those real-host comparisons, lifecycle gating, UI, charts, session ownership or performance-target verification.

Verification on 2026-10-15 with the established local .NET SDK: focused Stats checks passed 12/12, the full dependency-free harness passed 350/350, and the Release solution build succeeded with zero warnings/errors. The first full harness run had a timeout in the existing volume actor/event test (349/350); the complete rerun passed. These results were obtained on macOS 26.7.1 and do not replace the real Windows/daemon checks above.
