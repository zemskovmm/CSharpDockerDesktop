# Network deletion preparation

`DesktopSession` implements `INetworkDeletionPreparation` in Application, borrowing the negotiated connection's `INetworkReader`. Preparation performs only a fresh network Inspect. It never invokes `INetworkCommands`, reuses displayed inspection, derives attachment evidence from list metadata, removes dependencies, or owns a connection/retry loop. The [Application deletion coordinator](network-operations.md) atomically consumes eligible preparation; confirmation UI remains pending.

The caller captures `NetworkDeletionTarget(ConnectionGeneration, Id)` using the complete original ID from current network rows. IDs and attachment map keys remain ordinal, opaque and untrimmed. Invalid IDs, absent rows, stale generations, unavailable readers, canceled callers and exhausted replacement capacity produce classified rejection snapshots without replacing retained preparation. Resource names, endpoint/container metadata, labels, raw Inspect and daemon errors remain private in-memory evidence and have no automatic logging/transmission path.

Each accepted request gets a new preparation ID and revision. Its immutable snapshot separates acquisition phase/failure from eligibility and reasons. A completed identity-matched Inspect can be blocked: built-in `bridge`, `host` and `none` evidence from either the captured row or Inspect blocks eligibility, even when those sources contradict each other. Any inspected attachments are dependencies. Missing attachments are unavailable evidence, distinct from an observed empty map. Unusable names, differing row/Inspect names, or malformed attachment evidence cannot establish permission. A different inspected ID is classified malformed acquisition evidence and is retained for deliberate review, never accepted as the target. Collection snapshots are copied into read-only containers; raw JSON preserves the actual inspected response.

A fresh identity-matched Inspect with a usable non-built-in name, no contradictory captured name, and observed empty attachments can establish `PrecheckEligible`. Optional driver/IPAM/scope/endpoint fields can remain unavailable and are preserved as such. Eligibility is only a local precheck: Docker's inspected attachment map is not proof of cluster-wide completeness and the resource can change before deletion. A future single-use confirmation/command coordinator must recheck exact preparation identity/revision/currentness, atomically consume it, dispatch only ordinary non-force deletion and handle the daemon's final dependency/conflict response. This contract alone never authorizes or executes deletion.

Preparation is independent of current visual selection. Relevant exact full-ID network events, unusable event identities, observation recovery gaps, authoritative target disappearance, contradictory later row names, explicit invalidation and connection changes synchronously fence current evidence under the session lock. Unrelated identifiable network events do not fence another target. Events do not trigger automatic preparation retries. Invalidated evidence can remain visible for explanation, with unknown eligibility; late success or failure cannot restore eligibility. Reconnection requires a new explicit preparation for any new mutation; a previously admitted operation may recover observation only under its stricter endpoint/Engine identity contract. `IsNetworkDeletionPreparationCurrent` requires the exact identity/revision and eligible current evidence. Close accepts the same preparation ID at any revision, fences it and joins owned work. A different preparation ID cannot close a replacement.

There is at most one active preparation Inspect and one waiting replacement, independent of the single browsing read coordinator, event stream, Logs and other resource families. Replacing cancels/fences its predecessor and waits for it before starting another Inspect; excess requests are rejected. The request deadline includes that waiting time. An independent deadline still bounds connection continuity when a superseded or event-fenced reader ignores cancellation. Classified transport loss/deadlines feed existing session recovery. No second retry owner is introduced. Cancellation, close, retry, disconnect and disposal fence publication first; joined workflows retain the connection until even non-cooperative borrowed work returns. No implementation can forcibly finish an arbitrary non-cooperative capability; shutdown remains asynchronous and retains ownership until it returns. Observer notifications can arrive off the UI thread and exceptions are isolated; consumers should read the latest immutable snapshot and marshal rendering themselves.

## Verification evidence

The executable harness uses controlled Inspect completions, event barriers and controlled recovery delays. Seven network preparation groups cover empty/attached networks, all built-in names from either source, unavailable/contradictory evidence, immutable private metadata, opaque exact IDs and mismatches, admission rejection, fresh acquisition despite cached detail, selection independence, invalidation before/during/after Inspect, usable/unusable/unrelated event identities, observation recovery, target disappearance, classified failures, cancellation, synchronous cancellation registration, replacement capacity, whole deadlines, reconnection, late non-cooperative completion, observer failures, joined shutdown and coexistence with browsing/events/Logs. A fake command capability fails if preparation invokes it. Focused invocation is `--network-preparation`; the complete harness remains the acceptance run.

These are simulated capability and transport-contract checks on macOS, not live Windows/Docker evidence. Outstanding real evidence includes non-elevated named-pipe operation on Windows, built-in and custom/driver/Swarm attachment behavior against actual daemons, deletion-time races handled by the future coordinator, and workstation resource/performance measurements. No successful simulation claims cluster-wide completeness or real Docker deletion safety.

On 2026-10-15, the final complete harness passed **312/312 groups on macOS 26.7.1**, and the Release solution build passed with zero warnings/errors using the established .NET SDK environment. The initial complete run passed 311/312: the new reconnect test timed out at `NetworkPreparationChecks.NetworkPreparationDeadlineRecoveryAndReconnection` while waiting for the replacement list because the fixture released a canceled liveness delay. The corrected fixture explicitly selects the live recovery delay. No existing intermittent session-test stall persisted in either complete run. One overlapping build invocation failed with MSB4166 (build child-node exit); a serialized final solution build succeeded. Logs are retained locally in `/private/tmp/network-preparation-harness.log`, `/private/tmp/network-preparation-harness-final.log`, `/private/tmp/network-preparation-focused-final.log` and `/private/tmp/network-preparation-build-final.log`. Race evidence comes from the controlled cases above, not a retry alone.
