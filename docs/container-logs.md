# Negotiated read-only container logs

A successful connection exposes the borrowed Application `IContainerLogSource` capability. `OpenLogsAsync(ContainerLogRequest)` inspects one container, resolves its full identity and authoritative `Config.Tty`, and opens `/containers/{id}/logs` through the selected API. The capability requires no Uno types or Infrastructure types. Application-owned DesktopSession coordination, bounded view storage and recovery are documented in [container-log-sessions.md](container-log-sessions.md). Search/filtering, autoscroll and presentation controls remain subsequent work.

`TailLines` is a required finite nonnegative count; the default maximum is 10,000. Zero requests no historical output. Negative counts, counts above the configured maximum, empty/oversized identities, traversal identities, null requests and invalid cursors fail before transport creation. The API's unbounded `tail=all` is never sent. Both stdout and stderr are requested, with timestamps enabled and details disabled. `Follow` is explicit. A nullable `Since` encodes exact nonnegative Unix seconds and a 0–999,999,999 nanosecond fraction as invariant `seconds.nnnnnnnnn`; null omits the cursor. No `until` is supplied. Tail limits are a requested history bound, not a byte-size guarantee from an untrusted daemon.

Opening returns an owned `IContainerLogSubscription` or a classified failure. Its `ContainerId` is the full identity established by inspection, preventing a deleted/recreated name from selecting a different container between inspection and logs. Caller cancellation while opening throws OperationCanceledException after cleanup. Cancellation of an established subscription is normal `Canceled` completion. Consumer cancellation of a channel read alone does not cancel the subscription: dispose it or cancel the token passed to opening.

## Output and timestamps

`Output` delivers bounded `ContainerLogOutput` fragments. Text preserves exact UTF-8 characters and all line endings, including the original timestamp prefixes, without normalization or deduplication. A recognized leading RFC3339 timestamp is also available as `Timestamp.Original`, signed Unix seconds, and nanoseconds; it never passes through fractional DateTime ticks or floating point. `Timestamp.Cursor` is available for nonnegative timestamps. Missing/unrecognized prefixes remain in Text and have null metadata. `TimestampPrefixCharacters` includes the separating space and appears only on the first fragment of a recognized boundary, allowing a caller to deliberately remove display decoration.

Non-TTY output uses Docker's eight-byte multiplex header: stdout=1, stderr=2, system error=3, three zero reserved bytes, and an unsigned big-endian uint32 payload length. Frames yield stdout/stderr boundaries, including valid empty frames. TTY output remains `Combined`; neither payload bytes nor content-type guesses determine TTY. Its only observable boundaries are LF-delimited combined lines, with a final non-newline boundary on EOF. CR and LF are retained exactly. Docker does not expose the original stdout/stderr identity or underlying log-message boundaries for TTY output. Timestamps injected into partial TTY messages inside a long line remain in original Text; the implementation recognizes metadata at the observable boundary start, avoiding invented boundaries based on timestamp-looking user content.

`Sequence` and `BoundaryId` increase within a subscription and are not stable daemon IDs. `StartsBoundary` and `EndsBoundary` distinguish partial/complete output; empty end markers are legitimate and carry no displayed content. Chunk sizes are not stable identifiers. Long lines/frames produce many fragments with one boundary ID; callers must apply their own bounded assembly/retention instead of concatenating them without limit. Decoder state belongs to each logical stream across frames. If a UTF-8 character spans two frames of one stream, the complete character is delivered in the later frame; empty markers retain both frame boundaries. Character sequences, line endings and content remain intact across arbitrary reads and frame splits, including another stream interleaved between split character bytes.

These fields let a later coordinator retain a bounded recent window and choose an earlier exact timestamp cursor. Repeated text and timestamps are legitimate output and are always delivered. This layer never reopens, retries, selects overlap, or deduplicates. TTY recovery must account for its weaker observable boundaries; raw timestamped text remains available for conservative overlap handling.

## Completion and failure

Read until the channel finishes and then inspect `Completion`, which completes after response/transport cleanup. `CleanEnd` means a normally terminated HTTP body, including finite historical EOF and follow ending after a stopped container; EOF itself is not evidence of a transport exception. `Canceled` covers caller-token or owner/caller disposal. `Failed` contains a `ContainerLogFailure` with distinct invalid-request, admission-limit, opening-deadline, container-not-found, access-denied, logging-unavailable, daemon-error, malformed-output, and transport-loss kinds.

Headers with unsupported stream types or nonzero reserved bytes fail as malformed output. EOF inside a header/payload and incomplete/malformed UTF-8 fail predictably; strict decoding does not replace malformed bytes. Complete previously delivered fragments remain available on malformed/daemon failure, but there is no promise to emit a valid character prefix from the same decoder batch that contains malformed text. A truncated payload has no end marker. Empty historical streams and complete empty frames terminate cleanly.

HTTP 404 is NotFound; 401/403 is AccessDenied; other 4xx is InvalidRequest; other errors are DaemonError unless the daemon establishes its known unavailable logging capability diagnostic. Inspect explicitly reporting logging type `none` is also LoggingUnavailable. Arbitrary driver names are not treated as proof that reading is unsupported, because drivers can supply a readable cache. System-error frames report bounded daemon messages separately from output, including the known unavailable diagnostic. TTY has no separate in-band error channel: raw combined text is preserved, with no attempt to classify user text as daemon errors.

Original daemon messages are bounded and separated from fixed descriptions, with explicit truncation information. Oversized HTTP bodies retain a bounded original byte prefix rather than parse incomplete JSON; complete JSON errors expose their message field. These values and log contents are never automatically logged or transmitted.

## Ownership and budgets

Each admitted subscription owns one independent HTTP/pipe pool. It freshly negotiates readiness/version/info and compares Engine ID, Engine version, full API negotiation and OS type with its owning selected connection before inspection/opening. Reopened transport generations invalidate the subscription. Metadata agreement alone cannot prove that an identically configured daemon has never restarted; later authoritative reconciliation remains necessary. Logs do not occupy the retained ordinary pool or the event pool.

Admission includes opening, established, naturally completed, canceled, and disposing subscriptions. Dispose the caller-owned subscription to release capacity; a failed opening joins cleanup and releases its slot before returning. Owner disposal cancels and joins all admitted openings/producers, disposes their responses/pools, and prevents obsolete buffered delivery. Caller disposal has the same effect for one subscription. Disposal is idempotent and joined, even if a transport returns late. Cancellation unblocks both pending reads and channel writes. Natural completion retains buffered output until read/disposal; cancellation and continuity loss clear it and guard subsequent reads.

Validated defaults in `DockerConnectionOptions` are implementation tuning, not product performance promises:

| Setting | Default | Valid range |
| --- | --- | --- |
| LogOpeningTimeout | 10 seconds | Positive, representable cancellation delay |
| MaximumConcurrentLogSubscriptions | 4 | 1–64 |
| MaximumLogTailLines | 10,000 | 1–1,000,000 |
| LogBufferCapacity | 128 units | 1–4,096 |
| MaximumLogFragmentCharacters | 4,096 UTF-16 characters | 64–65,536 |
| MaximumLogErrorBytes | 64 KiB | 64 bytes–1 MiB |

The decoder has a fixed 4 KiB read buffer, eight-byte header, at most three UTF-8 decoder states and one active bounded character buffer plus a 64-byte timestamp-prefix buffer. No allocation follows the announced frame length or line length. Delivery retains at most channel capacity plus one pending fragment; it waits under backpressure and never drops output. Inspection uses `MaximumResponseBytes` with bounded JSON depth. HTTP/system error content uses the independent error budget. With defaults, ordinary + event + four logs subscriptions require at most six simultaneous retained pipes, each independent. A slow or absent consumer bounds memory by stopping further reads.

The total opening deadline covers fresh negotiation, inspection, response headers and stream acquisition; handshake steps also use ordinary short-request deadlines. Established streams have no ordinary short-request timeout, including historical reads: they terminate by EOF, explicit cancellation, disposal, or failure. The layer performs no retries.

## Official contracts and verification evidence

The [official API 1.40](https://docs.docker.com/reference/api/engine/version/v1.40/) and [API 1.56](https://docs.docker.com/reference/api/engine/version/v1.56/) references establish the GET endpoint, finite tail/follow/timestamp controls, 404 and server failures, and attach-style framing. All 17 official OpenAPI specifications for 1.40–1.56 were retrieved on 2026-10-14. `Fixtures/Logs/contract-evidence.json` records source URLs, SHA-256 digests, projected parameter/status contracts and explicit synthetic request fixtures. These endpoint checks use negotiated API paths throughout; the client maximum remains its current supported 1.56.

The OpenAPI `since` field is described as integer even though the daemon accepts exact fractional cursors. This implementation deliberately follows the official [Docker 19.03 daemon parser](https://github.com/moby/moby/blob/v19.03.0/daemon/logs.go) at the API 1.40 baseline and [Moby timestamp parser](https://github.com/moby/moby/blob/v28.0.0/api/types/time/timestamp.go), which accept seconds plus nanoseconds. [Moby's logs route](https://github.com/moby/moby/blob/v28.0.0/api/server/router/container/container_routes.go) establishes TTY-based framing and non-TTY multiplexed content type from API 1.42. [WriteLogStream](https://github.com/moby/moby/blob/v28.0.0/api/server/httputils/write_log_stream.go) establishes fixed nanosecond prefixes and in-band system errors; [stdcopy](https://github.com/moby/moby/blob/v28.0.0/pkg/stdcopy/stdcopy.go) establishes the framing bytes.

The independent deterministic harness passes **93/93 groups on macOS 26.7.1**, including eight logs groups and all applicable existing checks. The solution builds with zero warnings/errors. Fixtures cover every supported API path, exact cursors, finite history/follow, authoritative TTY, multiplexed stream identity, repeated content, randomized/one-byte framing and UTF-8 fragmentation, character splits across frames/streams, line endings, 200,000-character lines, uint32-max announced payloads, strict malformed text/header handling, partial/clean EOF, timestamp offsets and nanoseconds, bounded error bodies, unsupported drivers/not-found, admission including openings, backpressure, blocked cancellation, owner continuity loss, long-lived follow, and late-opening/disposal races.

The controlled three-pipe server exercises actual NamedPipeClientStream/SocketsHttpHandler HTTP chunk decoding while logs and events are active and ordinary liveness, list, inspect and start requests succeed. It proves transport ownership/framing under the host's .NET implementation. It does **not** establish real Windows Docker Desktop/WSL2 access, ACL semantics, daemon logging-driver behavior, or real restart/reconnect behavior. Those Windows daemon checks remain unavailable here; no runtime daemon capture or GUI logs behavior is claimed by this task.
