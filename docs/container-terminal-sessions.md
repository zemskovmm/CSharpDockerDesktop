# Application interactive exec sessions

`DesktopSession` implements `IContainerTerminal` using the retained negotiated connection's borrowed `IContainerExec` capability. Presentation receives session state and raw immutable byte chunks; it never receives a connection, capability, or owned attachment. No shell, default argv, command picker, renderer, or durable tuning policy is selected here.

## Opening and ownership

The caller explicitly supplies the selected full 64-character container identity, bounded argv, and positive columns/rows (1–65535). Arguments are copied before I/O. Admission returns a classified result and local session identity. Accepted means coordination was admitted, not that creation/start succeeded. The immutable snapshot also captures the selected connection generation. The shared authoritative container inspector must establish running=true and paused=false. Unknown or invalidated lifecycle fields cause a fresh inspection; labels from the list cannot authorize exec. Known stopped/paused states reject admission. Missing/unavailable state produces a classified interruption/rejection rather than starting a container.

One establishment runner owns at most one active request and one latest pending replacement. Replacement immediately revokes the previous consumer, then waits for its cleanup before dispatching the next request. A canceled noncooperative capability is joined; no replacement task chain accumulates. The connection owner joins the terminal runner before disposing its connection. Lifecycle observations invalidate eligibility and request authoritative inspection through the existing container scheduler. All waiters observe the same eligibility broadcast. Authoritative stop, pause, disappearance, selection/navigation changes, and connection invalidation revoke output and admission. A transport failure invokes the existing connection recovery owner; a replacement connection never reopens the interrupted exec. Opening another exec always requires a new explicit call.

Creation is dispatched once. Start is dispatched once on that exact usable acknowledged binding. Creation and start dispositions remain separate historical evidence, including late acknowledged identity or late established/upgrade evidence after cancellation. Neither identity nor acknowledgement proves the process ran. There are no retries of creation/start, uncertain resize, or possibly written input.

## Output and explicit input

The owner forwards the combined TTY bytes without UTF-8, ANSI/VT, or Docker multiplex interpretation. Its bounded Channel uses lossless backpressure, independently of the attachment's own transport budget and of Logs, Stats, and Events. Oversized fragments are split into bounded immutable chunks, preserving order. One consumer wait is admitted at a time; cancellation of that wait does not cancel the terminal. Reads carry a session identity and a revoked/completed distinction. Before delivering an asynchronously fetched chunk, a consumer must check `IsContainerTerminalCurrent(sessionId, containerId, connectionGeneration)` in its delivery callback. A prior identity, wrong container, closed request, or invalidated lifecycle cannot publish bytes.

Input is explicit bounded bytes, copied before asynchronous I/O. Only one write is admitted and no input is queued. Written/NotWritten/Uncertain outcomes remain available to the caller and the latest admitted result is retained privately. Cancellation/uncertainty never replays bytes. Uncertain input interrupts further admission. A byte `0x03` is forwarded unchanged; there is no terminal path to container Stop or another lifecycle command. Closing releases client resources and never claims to terminate the exec process.

Initial dimensions are submitted through the existing exact-binding resize primitive. There is one dispatched resize and one latest pending dimensions request. Superseded pending callers receive NotDispatched; a dispatched caller retains its actual historical result even during close. An acknowledgement is an HTTP outcome, not evidence of actual rendered dimensions. A later explicit request is a new request, including after uncertainty.

## Process evidence, EOF, and cleanup

Cancelable, deadline-bounded exec inspection runs serially while attached, then performs a bounded observation after attachment EOF. Null fields stay unknown. Observed false/zero are daemon fields, not inferred successful start or exit. EOF, canceled client work, a closed tab, and attachment cleanup never prove process death. Once inactive or after EOF observation completes, there is no continuing polling. Inspection failures are exposed separately from creation/start and attachment outcomes. Private daemon response/failure evidence can explain missing commands and daemon rejection without putting command/output text into normal state or notifications.

Normal EOF closes the producer but preserves accepted output for draining. Explicit close, replacement, disappearance, or disconnect revoke buffered delivery immediately. Close returns a task that joins the work already owned at that boundary: establishment, late attachment ownership/disposal, inspection, input, resize, admitted output waiting, cancellation callbacks, and notification work. Repeated close/dispose joins existing cleanup. Cancellation fences state before borrowed callbacks run, including reentrant callbacks. A noncooperative capability can delay that join indefinitely; the owner keeps it bounded to the existing running work and one pending replacement rather than abandoning it or leaking a late attachment. A new explicitly opened session is not joined by an earlier close.

## Finite implementation defaults

Defaults are independently configurable coordination budgets, not product policy:

- 128 arguments, 4 KiB UTF-8 per argument, 32 KiB combined argv.
- Output: 16 queued chunks of at most 4 KiB (64 KiB queued), plus one bounded ingestion chunk and the borrowed transport's separate fragment/channel budget. Caller-retained returned bytes are outside owner retention.
- One admitted output wait, one input write of at most 4 KiB, no pending input, one dispatched resize and one latest pending resize.
- Fixed evidence slots: creation, start (without an attachment reference), latest inspection (without process argv/configuration), latest resize, latest input, and cleanup failure. Each raw response body, daemon message, and failure description is capped at 8 KiB independently; resize can have its response and binding-response slots. There is no outcome history. Superseded request evidence is released after its joined cleanup.
- Establishment/lifecycle admission and each input, resize, or inspection operation have a 20-second cancellation deadline. The deadline does not authorize abandoned noncooperative work or a retry. Established streams have no short-request deadline.
- Attached inspection cadence is two seconds; EOF gets one final bounded observation. State notifications coalesce at 50 ms on background work. Output fragments never schedule observer notifications. One notification task and at most one pending batch serve rapid replacements; a close captures only the batches already owned.

`ContainerTerminalSnapshot`, output/evidence wrappers, and protocol outcome/failure string representations omit argv, bytes, raw bodies, and daemon descriptions. Notifications contain no payload. Evidence is deliberately requested through `ReadContainerTerminalEvidence` and must not be automatically logged, exported, or attached to diagnostics. Caller-owned command strings and returned bytes are sensitive regardless of this owner's finite retention.

## Simulated evidence and remaining validation

The dependency-free Application harness uses controllable capabilities, bounded fake streams, late responses, blocked cleanup, and a manual TimeProvider. It exercises exact create/start binding; unknown/stopped/paused/missing admission and event invalidation; replacement/close during admission, creation, start, input, resize and inspection; late attachments; backpressure and raw byte order; EOF drain versus revocation; input uncertainty and Ctrl+C; resize coalescing and no replay; unknown and observed process fields; disconnect/recovery and navigation; reentrant cancellation; joined noncooperative cleanup; notification coalescing; bounded private evidence and sensitive representations; and simultaneous Logs/Stats.

These simulations establish Application coordination only. IDD-0013 terminal-surface selection/licensing research remains unresolved. Real Windows/Docker named-pipe interactive validation remains outstanding: duplex terminal exchange, shell/command failures, UTF-8 and ANSI/VT rendering, selection/copy/paste, resizing behavior, Ctrl+C, EOF, and resource closure must still be demonstrated with the eventual terminal surface. This change establishes neither terminal rendering nor full IDD-0008 terminal conformance.
