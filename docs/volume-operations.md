# Application volume deletion coordination

`DesktopSession` implements `IVolumeOperations`, borrowing `IVolumeCommands`, `IVolumeReader`, and `IVolumeDependencyReader` from its retained negotiated connection. This is an Application contract. The Volumes page still provides read-only browsing; deletion dialogs and presentation integration are pending. A future caller must display the complete preparation dependency evidence, explicitly identify incomplete evidence, warn that deletion can permanently remove data, and obtain deliberate confirmation before calling `ExecuteVolumeOperationAsync`. Empty dependencies never supply authorization.

The request captures the complete original ordinal volume name, browsing connection generation, and exact completed `VolumePreparationIdentity` (ID and revision). Admission validates and consumes that preparation under the same session lock used by preparation close/replacement, resource events, and connection changes. The operation retains the original immutable completed preparation, including every found running/stopped container identity and unverified candidate ID. The preparation exposed for future validation changes to `Consumed` with a newer revision. Existing incomplete evidence remains incomplete and usable for deliberate confirmation; unavailable evidence cannot admit deletion. Closed, failed, loading, invalidated, superseded, absent-target, wrong-revision and wrong-target evidence cannot admit a command.

Admission retains one operation and one completion receipt, with no operation queue or growing replay history. Identical retained admitted requests share completion, including after completion. Once another operation replaces that receipt, an old request still cannot consume its superseded preparation. Concurrent excess requests return classified NotDispatched results without replacing useful retained evidence or consuming a preparation. Fresh preparations are rejected while an operation or its borrowed work remains pending, preserving a bounded dependency-query budget. Selection, cleared Inspect, and navigation do not change an admitted name or cancel its reconciliation. Names are never trimmed, folded, shortened, or substituted. This boundary never requests force, deletes related containers, or retries a mutation.

## Retained outcomes

`VolumeOperation` is an immutable snapshot replaced under the session lock. `VolumeOperationChanged` can originate off-thread; observers read the latest snapshot and marshal it for display. Exceptions in observers are isolated without logging. Retention is bounded to one operation, its original preparation, latest listing/dependency observation, and counters. Domain dependency collections, nested names, and copied listing rows/labels/warnings are read-only.

| Evidence | Meaning |
| --- | --- |
| `CommandOutcome` | Original NotDispatched, Acknowledged, DaemonResponse, or Uncertain protocol evidence, with classified failure, HTTP status, original daemon message/body and unavailable-body flag. |
| `Interruption` | Caller cancellation, command deadline, or connection replacement remains distinct from later protocol evidence. |
| `NotDispatched` | No mutation dispatch is established, including classified cancellation before dispatch. |
| `ObservedAbsent` | A current complete authoritative list excludes the captured name, or current exact-target Inspect reports NotFound. |
| `ObservedPresent` | Current exact-target Inspect returned that complete ordinal name. |
| `Unresolved` | Bounded observations failed or were invalidated, conflict dependencies remained incomplete/unavailable/failed, or connection/shutdown interrupted reconciliation. |
| `ObservedListing`, read failures, `ObservationInvalidated` | Latest collection/warnings and separate list/target failures remain available as evidence; invalidated evidence cannot resolve state. |
| `RefreshedDependencies`, `DependencyObservationState` | Conflict-related fresh dependency evidence is complete, incomplete, unavailable, failed, or invalidated; it never becomes a new preparation. |

Acknowledgement alone never establishes absence. A daemon NotFound response is still command evidence requiring an authoritative read. Uncertain-but-absent and acknowledged-but-present are valid combinations. Names do not provide immutable identity: deleting and recreating a volume under the same name can produce `ObservedPresent`; the operation cannot attribute that presence or absence to its command. These are current observations at the reported connection generation, not causal or permanent claims.

Null collections and warning-bearing lists cannot establish absence or erase useful retained browsing rows. Reconciliation still performs exact-target Inspect after incomplete or failed lists unless transport continuity was lost. A current successful Inspect establishes presence; a current exact NotFound establishes absence even if the list was incomplete. Wrong returned names and other failed inspection remain unresolved. Private original daemon diagnostics, dependency identities, raw Inspect and resource metadata are never automatically logged or transmitted by this coordination.

## Scheduling, conflicts, and recovery

Every possibly dispatched result triggers observation, including daemon rejection, caller cancellation, lost responses and unknown exceptions. The existing volume read scheduler serializes full listing, targeted inspection and (after dependency conflict) dependency acquisition. One pending observation slot and a capacity-one signal retain bounded state. Ordinary browsing receives a turn between operation attempts, and existing list/detail fairness remains. Events continue on their existing shared connection subscription. Neither a browser refresh nor selection cancellation can cancel required operation reads or disable their independent deadline.

Dispatch and command-response fences reject older list/detail results. Relevant volume/container events and observation-stream gaps advance the operation observation revision. Late or event-obsolete reads cannot resolve the operation or republish obsolete browsing content. A newer event invalidates the whole list/Inspect/dependency observation; bounded follow-up acquires new evidence. On conflict the original daemon response remains available while current volume and running/stopped dependency evidence is refreshed. Complete dependency evidence may resolve current presence/absence. Incomplete/unavailable/failed evidence remains explicitly classified and finishes as `Unresolved` after the bounded budget, with any usable current presence observation retained separately. Refreshed dependencies never renew confirmation or authorize resend.

Caller cancellation controls the command token, and classified `VolumeCommandCanceledException.Outcome` is retained exactly. Possible-dispatch reconciliation uses the session lifetime rather than that caller token. A separate command clock continues to expire when a capability ignores cancellation. A command or read deadline and transport-loss evidence invalidate publication immediately and signal the existing shared connection owner; no second connection or automatic mutation retry is created. Late command evidence is retained privately, including acknowledgements and original daemon diagnostics, while the obsolete generation remains unable to publish authoritative state.

Recovery joins the old command, observations, preparation, browsing, events, Logs, and container/image operation work before disposing that connection. A new connection can resume observation only when the actual endpoint and a known nonempty Engine ID both match the command's origin. A different endpoint, changed Engine, missing current Engine ID, or unknown original Engine cannot establish the previous command's result. The original request generation stays unchanged, while resumed observations record the new generation. Retry and later Start perform observation only; mutation replay remains prohibited. A recovery pass has its own bounded observation budget.

Disconnect, Retry and disposal fence publication before canceling work. Connection disposal waits even for cancellation-ignoring command, list, Inspect, or dependency implementations. This can delay asynchronous teardown until the borrowed implementation returns, without releasing a connection while it is still borrowed. `VolumeOperationOptions` independently configures command timeout, follow-up interval and maximum observations (default four); ordinary observation deadlines use the existing session request timeout. `Observations` counts completed observation receipts; interrupted I/O may leave no completed receipt.

## Verification and limits

Nineteen focused deterministic harness groups cover exact preparation revision validation, atomic concurrent consumption, supersession/close/event invalidation, complete/incomplete/unavailable relationships, missing command capability, exact Unicode/whitespace/punctuation names, selection independence, bounded admission, completed and older receipt replay rejection, all command dispositions, classified cancellation before/after possible dispatch, late caller responses, conflicts and complete/incomplete/unavailable/failed dependency refresh, dependency event/transport races, acknowledged-but-present and uncertain-but-absent observations, null/warning lists and exact Inspect NotFound, pre-command/pre-response/event-obsolete reads, same-name recreation limitations, same/different/unknown Engine and changed-endpoint recovery, cooperative deadline evidence, non-cooperative command/list/Inspect/dependency joins, Retry/disconnect/disposal, isolated observers, and coexistence with active browsing, events, Logs and container/image operations.

These tests control capability responses and timing; they simulate daemon effects and do not mutate a real Docker Engine. Existing protocol fixtures and synthetic named-pipe HTTP tests provide separate lower-layer evidence. Real Windows non-elevated named-pipe access, Docker Desktop/WSL2 running/stopped dependencies, dependency races and data-loss behavior, alternative Engine compatibility, Windows delivery, and workstation performance still require real Windows/Docker evidence. A macOS harness or Release build cannot establish those claims.

On 2026-10-14, the complete dependency-free harness passed **240/240 groups on macOS 26.7.1 with .NET SDK 10.0.402**. The Release solution build succeeded with zero warnings and zero errors using the established isolated SDK/NuGet environment. These results include the nineteen new Application operation groups and all existing browsing, events, Logs, container/image operation, protocol, and presentation checks.
