# Read-only volume dependency acquisition

The retained negotiated Engine connection now exposes Application-owned `IVolumeDependencyReader`. `QueryVolumeDependenciesAsync` borrows the existing HTTP transport and cancellation lifetime. It takes one **complete original volume name**, preserving case, Unicode, punctuation and whitespace exactly through the existing volume-name validation. It does not resolve aliases, trim, normalize or interpret an image reference. There is no dependency database, browser-snapshot inference, mutation, automatic logging or transmission of container/volume metadata or daemon content. The [session-owned preparation contract](volume-deletion-preparation.md) coordinates explicit confirmation evidence; deletion coordination and UI remain pending.

## Authoritative requests and exact identity

The query sends `GET /v{negotiated}/containers/json?all=true&filters={encoded-json}`, with JSON `{"volume":["complete original name"]}`. JSON serialization followed by escaping the entire JSON query value protects names containing quotes, backslashes, slashes, percent signs, Unicode and query/fragment punctuation. It sends no status filter or list limit: `all=true` explicitly includes stopped as well as running containers.

The Docker filter contract accepts a volume name **or mount destination**. Candidate membership alone therefore cannot establish a volume dependency. Each returned full container ID is inspected with `GET /v{negotiated}/containers/{escaped-full-id}/json`, on the same retained connection. The inspected `Id` must equal the candidate's complete original ID. No shortened IDs or container names are used as request identities. Duplicate candidate IDs fail rather than silently combining potentially conflicting evidence.

A relationship is established only by inspected `Mounts` entries with `Type == "volume"` and `Name` equal to the complete requested volume name using ordinal comparison. `Source` and `Destination` are never treated as volume identities. Bind, named-pipe, tmpfs and image mounts do not establish volume relationships even when their paths or names happen to equal the requested name. Similar names, case variants, prefixes and encoded-looking strings do not match. Multiple matching mounts produce one related container.

The immutable Domain result retains the original volume name, full related container IDs, available list names/aliases, the inspection name, inspected runtime status and Running flag. A missing inspected status falls back to the available candidate-list state; this is evidence from an earlier daemon read, not a fabricated current state. Missing names/state remain null. Names are not shortened or sanitized for logging. Results do not retain raw container inspection/environment content. Constructors defensively copy collections into read-only wrappers.

## Empty, incomplete, unavailable and failed evidence

`EngineResourceResult<VolumeDependencies>` separates acquisition failure from acquired evidence. `VolumeDependencyCompleteness` separates the following successful response shapes:

- **Complete**: an available candidate array and usable mount evidence for every candidate. A genuinely empty array, or candidates all proven unrelated by inspection, produces a complete empty dependency collection.
- **Incomplete**: an available candidate array with at least one unverified candidate. Missing/null `Mounts`, missing mount type, or a volume mount missing its name cannot prove absence. Already established relationships remain available alongside `UnverifiedContainerIds`.
- **Unavailable**: a null candidate collection; the related collection stays null. This defensive handling of a non-authoritative null response never becomes empty evidence. The official successful list schema is an array.

Missing/null display metadata does not make otherwise usable relationship evidence incomplete. Unknown additive fields are tolerated. Invalid selected field/container types, duplicate selected fields, duplicate IDs, unusable/mismatched IDs, malformed JSON/Unicode/UTF-8, invalid present volume mount names or exceeded client budgets are MalformedData failures. Empty `Mounts` is usable empty mount evidence.

Cluster mounts (introduced in API 1.42) and future unknown mount types remain unverified rather than being silently counted as unrelated. Swarm cluster selectors/service/task relationships are not certified by an ordinary `Type=volume` name match. This query reports container evidence, not a Swarm service dependency inventory.

Any failed candidate inspection fails the query, including a 404 when a candidate disappears between listing and inspection. Previously acquired partial relationships are not published as complete evidence. HTTP 404 remains NotFound; 304/409 Conflict; 401/403 AccessDenied; other unsuccessful 4xx InvalidRequest; other unsuccessful status codes DaemonFailure. Original JSON `message` or plain-text daemon errors remain private data in `DaemonMessage`, separate from fixed safe descriptions. Oversized error responses retain status classification without a truncated message. Unauthorized transport access remains AccessDenied. Transport interruption, deadline, owner disposal or changed generation is TransportLoss. Caller cancellation throws normal `OperationCanceledException`, including cancellation wrapped by the transport. A call begun after owner disposal throws ObjectDisposedException.

## What the evidence establishes

The daemon filter supplies fresh daemon-visible candidates, and each successful inspection establishes the exact named-volume mounts reported for that container at that inspection instant. A complete empty result says that this sequence of daemon reads found no matching container dependencies. It does **not** prove that the requested volume exists, that permissions suffice for deletion, that inaccessible daemon data is visible, or that a deletion would succeed.

The list and inspections are separate reads, not a transactional snapshot. Container creation, removal, rename, runtime-state changes and mount/volume changes can happen during or after acquisition. In particular, a new dependency after the list may not be inspected. Transport continuity fences protect the negotiated connection's identity, not concurrent daemon resource changes. Later deletion must obtain fresh evidence for confirmation and handle the daemon's final dependency/conflict response; this query neither authorizes deletion nor eliminates the precheck/delete race. It never retries a mutation or automatically removes related containers.

## Bounds, cancellation and coexistence

Ordinary GET acquisition reuses `DockerResourceReader`: asynchronous headers/body reads, off-caller-thread JSON parsing, success/error body byte limits, and request/response/stream cleanup. A single whole-query deadline includes waiting for admission, listing and every candidate inspection. The configured default RequestTimeout remains five seconds. It is not reset between successful candidate reads.

At most two dependency queries are admitted by default, independently of commands and other resource reads. Each admitted query inspects one candidate at a time. The candidate count is capped at 4096 by default; selected strings are capped at 4096 UTF-16 code units without truncation. Additional retained inspected name/state characters are capped at MaximumResponseBytes for the whole query; candidate identities/names are already bounded by the list body. Excesses fail visibly rather than publishing a partial set. These are client safety bounds, not daemon schema limits or performance guarantees. Options configure the deadline, body/retention budget, candidate limit and query concurrency; option validation constrains these values. No live stream is opened.

Caller and connection-owner cancellation are linked across the whole query. Shared continuity and cancellation checks run before dispatch and after headers, body and decoding. The query checks them again after constructing the immutable result. Non-cooperative late responses cannot publish success after cancellation, expiry, owner disposal or generation change. Admission is released on all terminal paths. The borrowed capability owns neither the retained connection nor its handler, event subscription or Logs subscriptions. Its cancellation/cleanup leaves existing resource reads, commands, events, Logs and liveness usable.

## Official contract evidence and simulated verification

On 2026-10-14, all 17 official Docker API schemas from [1.40](https://docs.docker.com/reference/api/engine/version/v1.40.yaml) through [1.56](https://docs.docker.com/reference/api/engine/version/v1.56.yaml) were retrieved and inspected. They specify the list `all` boolean, JSON `map[string][]string` filters, `volume` name-or-destination filter, container inspection ID/name path parameter, full ID and available name/state metadata, and MountPoint type/name/source/destination semantics. List declares 200/400/500; inspection declares 200/404/500. The [Moby daemon list implementation](https://github.com/moby/moby/blob/v28.5.1/daemon/list.go) provides supplementary implementation evidence that volume filters can select mount destinations, names or sources; this is why inspection—not filter membership—establishes a relationship. This implementation evidence is not a promise about every compatible daemon.

`tests/CSharpDockerDesktop.Connection.Tests/Fixtures/VolumeDependencies/contract-evidence.json` records each official URL, SHA-256, retrieval date, request parameters, response codes, MountPoint field types and mount enums. Harness list/inspection responses are **synthetic**, constructed from these contracts, not captured from a Docker daemon. The harness negotiates all 17 supported versions, asserts the actual query/filter/inspection encoding, full identities, running/stopped dependencies, unrelated/bind mounts and immutable metadata. It also covers complete empty versus unavailable/incomplete evidence, malformed selected data, sensitive original daemon messages, HTTP/transport classification, known/unknown-length bodies, candidate limits, caller/header/body cancellation, wrapped cancellation, owner disposal, whole-query deadlines, bounded admission, non-cooperative late headers/bodies, transport-generation changes and shared decoder publication fences.

The simultaneous named-pipe fixture uses real SocketsHttpHandler with synthetic HTTP servers while events and Logs remain active. Dependency reads coexist with volume/container/image reads, container/image commands and liveness. Exactly three existing independent handshakes remain (ordinary requests, Logs, events): querying dependencies adds none. Queued dependency cancellation also leaves admitted reads and liveness usable.

On 2026-10-14, the dependency-free executable harness passed **207/207 groups on macOS 26.7.1 with .NET SDK 10.0.402**. The Release solution build succeeded with **zero warnings and zero errors**. No project verification policy file exists. These simulations do not establish real Windows named-pipe ACLs, Docker Desktop/WSL2 driver/cluster-volume behavior, stopped-container dependencies on a running real daemon, concurrent attachment/deletion semantics on that daemon, Windows delivery or workstation performance targets. Real Windows/Docker verification remains outstanding.
