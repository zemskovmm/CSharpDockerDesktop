# Container lifecycle commands and coordination

The negotiated Docker connection implements Application's `IContainerCommands`, alongside `IContainerReader` and `IEngineEventSource`. Start, Stop, Restart and Delete are asynchronous, cancellable borrowed calls. They share the retained ordinary HTTP pool and cannot dispose or replace its owner. Domain outcome types and the Application boundary have no Uno or HTTP dependency. DesktopSession now owns pending-operation coordination and authoritative reconciliation through these capabilities. The Containers screen now consumes `IContainerOperations` for state-aware single-container actions, explicit deletion confirmations and retained outcomes. [Presentation safety and local interaction evidence](container-acquisition.md#container-lifecycle-presentation) describe the delivered UI.

Commands accept an ID or Docker name, including the canonical single leading slash supplied by Inspect. Input must start with an ASCII alphanumeric character after that optional slash and contain only ASCII alphanumerics, underscore, dash or dot, with at most 4096 characters. The original validated identity is escaped as one path segment. Empty, dot-segment, control-character, invalid Unicode and query/path injection inputs never dispatch. The validation intentionally excludes arbitrary opaque strings accepted by the read-only Inspect helper. An optional Stop/Restart grace period is a nonnegative integer in seconds; null omits `t` and uses the daemon's configured default. Indefinite `t=-1`, signal overrides and detach/checkpoint options are unavailable.

| Operation | Negotiated endpoint | Parameters | Acknowledgement |
| --- | --- | --- | --- |
| Start | `POST /v<api>/containers/<identity>/start` | None | 204 accepted; 304 already started |
| Stop | `POST /v<api>/containers/<identity>/stop` | Optional `t=<seconds>` | 204 accepted; 304 already stopped |
| Restart | `POST /v<api>/containers/<identity>/restart` | Optional `t=<seconds>` | 204 accepted |
| Delete | `DELETE /v<api>/containers/<identity>` | Always `force=false&v=false`; explicit force choice sends `force=true&v=false` | 204 accepted |

Delete never issues Stop first, chooses force automatically, removes volumes, retries a conflict, or changes parameters after failure. The caller must deliberately select force and provide the future confirmation UI. No command is inferred from local state; the daemon owns permission/state races.

## Outcome and cancellation contract

`ContainerCommandResult` records the operation, disposition, available HTTP status, original daemon message, acknowledgement or classified failure. It intentionally does not retain the resource identity. `RequiresReconciliation` is true for every dispatched operation, including acknowledgements and daemon rejections.

| Disposition | Meaning |
| --- | --- |
| NotDispatched | Local validation, stale/disposed connection, capacity rejection or pre-dispatch cancellation prevented HTTP dispatch. |
| Acknowledged | Endpoint-specific 204 or Start/Stop 304 response received on the retained connection. This does not establish final state. |
| DaemonResponse | A different explicit response was received. The original status/message remain available. |
| Uncertain | Dispatch began but response, deadline, cancellation, disposal or connection continuity prevented a trustworthy completed result. The mutation may have happened. |

Dispatch is conservatively defined as entering `HttpClient.SendAsync`; an internal queue/write failure can therefore produce Uncertain even if the server actually received nothing. This avoids claiming non-application without evidence. A lost response must never authorize automatic replay. The coordinator must read actual Engine state, using a freshly negotiated connection after transport loss; deletion can reconcile with absence, while Start/Stop/Restart must account for concurrent external changes.

Caller cancellation throws `ContainerCommandCanceledException`, a normal `OperationCanceledException`. Its `Outcome` retains NotDispatched or Uncertain, available response evidence and reconciliation requirements. Catching it as the ordinary base exception remains valid, but command coordinators must inspect the subtype to preserve uncertainty. Cancellation before dispatch sends nothing; cancellation after dispatch never promises rollback. Cancellation takes precedence even when the transport wraps it. Connection disposal is instead a classified result, with Uncertain for already issued operations and NotDispatched for later calls.

404 remains NotFound, 409 Conflict, 400/other 4xx InvalidRequest, 401/403 AccessDenied, and 5xx DaemonFailure. Operating-system access denial remains distinguishable from TransportFailure. Unsupported acknowledgement statuses (including Restart/Delete 304 and arbitrary 200/202) are UnexpectedResponse, never success. HTTP 500 remains DaemonFailure even when its message describes a state problem: the client does not guess a stronger classification from sensitive text. Deadline, disposal and stale continuity are separate failure kinds. Original JSON `message` or plain non-JSON text is preserved when the complete body fits the budget; oversized or interrupted bodies have `ErrorBodyUnavailable=true` and preserve available HTTP status. Routine descriptions exclude identities, daemon content and other sensitive data; there is no automatic logging.

## Transport replay and lifetime

The official [.NET 10 HTTP pool implementation](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Net.Http/src/System/Net/Http/SocketsHttpHandler/ConnectionPool/HttpConnectionPool.cs) retries `RetryOnConnectionFailure` on established connections, independently of application retry code. The ordinary pool has one physical HTTP connection. After successful handshake, its pipe counter is sealed: every subsequent ConnectCallback refuses a replacement before opening it, invalidates continuity and requires an explicit fresh handshake. The guard checks both before connecting and before handing over a newly opened stream, covering a racing seal. Commands also check retained generation before dispatch, observe continuity while in flight and require exact HTTP/1.1. Redirects/proxies are disabled and no authentication/retry policy is configured. Consequently implicit HTTP stale-socket recovery cannot replay a mutation to an unnegotiated replacement daemon. Read and event pools use the same sealing rule; events independently negotiate their dedicated pool. Loss requires a fresh connection, rather than transparent reopening underneath old metadata.

Requests, responses, bounded error streams and temporary buffers are disposed on every exit path. Cancellation sources and command slots are released; borrowed commands keep the owner's HTTP transport alive. Owner disposal cancels in-flight HTTP work. In-flight operations bound their own completion through linked deadlines. No separate command transport, persisted queue or resource-state cache is introduced.

Current `DockerConnectionOptions` tuning defaults are 30 seconds for Start/Delete and two minutes for graceful Stop/Restart, independent of the five-second read deadline. The grace-period `t` is a daemon wait parameter, distinct from the local overall operation deadline: a large daemon default or explicit `t` can outlast that deadline and produce Uncertain. Hosts can configure both finite lifetimes. Error retention defaults to 64 KiB (configurable from 64 bytes to one MiB); at most the limit plus one byte is read to detect an unknown-length overflow. Four concurrent command calls are admitted per connection (configurable 1–64); excess calls fail locally rather than enter an unbounded command queue. The ordinary pool still issues one request at a time. These numbers are implementation tuning, not product latency guarantees.

## Application operation contract

`DesktopSession` implements `IContainerOperations`. Presentation can submit a `ContainerOperationRequest` with a `ContainerIdentity` containing the complete ID from `ContainerSnapshot` and that snapshot's `ConnectionGeneration`. Partial IDs, Docker names, stale generations and invalid action parameters are rejected without dispatch. Delete defaults to `ForceDelete=false`; explicit force is forwarded once to the protocol capability, which always preserves volumes. Confirmation belongs to the future Presentation caller.

`ContainerOperation` retains one immutable `ContainerOperationSnapshot`, and `ContainerOperationChanged` announces updates off the UI thread. The snapshot exposes requested identity/action/parameters, CommandPending or Reconciling phase, original protocol outcome, classified observation failure, observed existence/runtime state, observation count and the generation that supplied that observation. Completion is separate from outcome: ObservedRequestedState describes current authoritative evidence, ObservedDifferentState accompanies a reconciled daemon rejection, NotDispatched preserves proof of no dispatch, and Unresolved never claims success. A preserved daemon failure remains available even when an external action left the resource in the requested state. Original daemon messages are available only for deliberate display; the coordinator does not log them.

There is one accepted operation at a time, no mutation queue and no bulk behavior. Identical pending requests share the same task; different pending requests receive a local capacity result and do not overwrite the retained operation. Rejected requests are returned to the caller without replacing the retained operation. Caller cancellation prevents dispatch when possible. After possible dispatch, `ContainerCommandCanceledException.Outcome` determines the need for observation; caller cancellation does not discard reconciliation or promise rollback.

All dispatched outcomes, including acknowledgement, conflict, not-found, unexpected response and uncertain cancellation, initiate list/target-inspection reconciliation. Command dispatch and completion fence off older reads. Verification shares the existing serialized container read loop, inspects the command target even when deselected, and never changes selection to perform verification. Current selected details/Inspect are cleared when invalidated and refreshed from authoritative data. A missing target is removed and its selected inspection is cleared. Closing or replacing selection during verification cannot reopen old details. Interrupted unrelated inspections are retained for a new read. Events invalidate crossed observations instead of supplying final properties.

An acknowledged transition can continue after the response. Start requires an observed running, unpaused, non-restarting, non-dead state; Stop requires observed non-running and non-restarting state; Delete requires authoritative absence. Restart takes an authoritative pre-dispatch start-time baseline and requires a later start time with stable running state. Missing start-time evidence leaves Restart unresolved even if it looks running. These observations establish resource state, not that this command caused it. Bounded follow-up reads expose continued transitions or uncertainty without replaying the mutation.

`ContainerOperationOptions` defaults to four post-command observations, a 250 ms follow-up interval and a 90-second command budget. A reconciliation list/inspection pair also has the finite request budget configured by `ConnectionRecoveryOptions.OperationTimeout` (20 seconds by default). Defaults are tuning choices; slow or stalled I/O does not block navigation, selection or manual refresh. The coordinator retains one operation, one pending observation request and at most one command plus one serialized container read. Connection retry, explicit `DisconnectAsync`, transport loss and disposal invalidate publication, cancel owned work and join even cancellation-ignoring completions before disposing the borrowed connection.

A command-detected transport failure enters the existing recovery workflow. A fresh connection to the same endpoint/Engine identity obtains its ordinary initial authoritative snapshot and resumes observation of the unresolved operation, retaining the original request generation while recording the new observed generation. It does not dispatch the command again. A replacement Engine identity does not resolve an old Engine's operation. Reconnection never uses a late result from the retired generation to update current resource state.

## Compatibility evidence and limitations

Reviewed on 2026-10-14: official Docker OpenAPI definitions for **every API 1.40–1.56**, specifically the four lifecycle endpoints, their methods, parameters and response statuses. [Selected contract evidence](../tests/CSharpDockerDesktop.Connection.Tests/Fixtures/Commands/contract-evidence.json) records each version's source URL and full-spec SHA-256 plus the selected endpoint contract. Sources include [Docker API 1.40](https://docs.docker.com/reference/api/engine/version/v1.40/) and [Docker API 1.56](https://docs.docker.com/reference/api/engine/version/v1.56/), with direct YAML links recorded for all intervening versions.

All 17 versions declare the acknowledgement/status sets above: Start 204/304/400/404/500; Stop 204/304/404/500; Restart 204/404/500; Delete 204/400/404/409/500. The common `t` integer and Delete's boolean `force`/`v` defaults support this capability throughout the range. Newer optional signal parameters do not need to be sent by this subset. General HTTP access denial/unexpected status handling is defensive behavior in addition to those documented sets. This lifecycle review is separate evidence from the previously reviewed read/event schemas.

The dependency-free harness tests each declared endpoint/status for each negotiated version; explicit/default delete safety and encoded identity; invalid identity and cancellation before dispatch; endpoint-specific 304 handling; original messages and distinct failures; applied mutations followed by lost responses; cancellation/deadline/disposal/continuity after issuance; command capacity, exact and excessive error bounds; suitable graceful lifetimes; request/response/stream cleanup; and continued reads/events. Actual `SocketsHttpHandler` named-pipe fixtures establish no blind replay to a waiting replacement pipe and show authoritative read recovery on an explicit fresh connection. Pipe fixtures also verify issued-command cancellation/deadline/disposal closes the active stream.

These are controlled protocol and transport fixtures on the local .NET host, not captured real Engine lifecycle transitions or Windows Docker/ACL integration evidence. They do not establish real-volume preservation across all storage drivers, Windows delivery, daemon-specific signal behavior, real-daemon convergence of the Application coordinator. Presentation confirmation is covered separately by controlled state checks and the synthetic graphical smoke host. Real Windows daemon lifecycle/volume smoke checks remain required for release evidence; DesktopSession consumes this capability through the verified operation contract; the Containers presentation now integrates it without duplicating dispatch or reconciliation.
